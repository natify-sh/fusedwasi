# Before the first release

fusedwasi is an alpha. The first release is the pre-release `0.1.0a1`; the owner sets the tag, and `publish.yml` builds and publishes it (the trusted publisher on PyPI is set up). It comes out when its interface is frozen **and shown neutral** (section 5), not when a particular user is ready. The users that exist today pin it by commit, so waiting costs them nothing; none of them is a condition of the release.

This file is a list of what to settle first. It is written 2026-10-26 from the code of the three repositories and from `host_scope.md`; an item marked **[check]** was not verified when this was written.

## 1. The public names

**Done 2026-10-27 (step 5).** The public names are listed in [`public_api.md`](public_api.md), made from `src/fusedwasi/public_api.json` (C and Python, a line of purpose each, the fields of the public structs; wasi:http and wasi:sockets marked unstable). Every other name is private and carries a mark (a double underscore after the prefix in C, a leading underscore in Python; `design_model.md`, section 5), and `tests/test_public_api.py` fails when a name is neither listed nor marked, when a listed name does not exist, and when a neutral user (`tests/neutral/`) uses a private name. The names that changed are in [`private_names.md`](private_names.md). The function of each import (`fusedwasi_p1_<name>`, `fusedwasi_wasi_<package>_<interface>_<name>`) is bound by name by the generators; those 247 names are public by being in the tables of signatures.

**Decided by the owner, 2026-10-27:** the helpers of the canonical ABI (`mem`, `load_*`, `store_*`, `alloc`, `string`, `table_get`) stay private; the kinds `FUSEDWASI_P2_KIND_*` (and `KIND_*` in Python) are public in both languages; the names of the transport and of the server side of `wasi:http` are public and marked unstable in the alpha.

## 2. Behaviour not yet checked against a real host

- 0.1 is held by the official wasi-testsuite (72 tests of the commit `9dfd486`), which **runs in the CI of fusedwasi** (job `python-wasmtime` of `neutral.yml`, fusedwasi as the WASI of wasmtime-py) and in the CI of a user. 0.2 is compared with the text of the WIT and between the C and the Python (`host_scope.md`, "Checked against the WIT"), and **with Wasmtime 50.0.1: `wasi:filesystem` (262 operations) and `wasi:http` (23 requests), in Python and in C, run on 2026-10-27 and again after the rewrite of 0.1 over 0.2 (0 differences that are not marked as known; `wasmtime_compare.md`); cli, clocks, random and WASI 0.1 as flat calls in Python and, since 2026-10-28, in C over wasm3 (`docs/experiments/wasmtime_compare`, `HOST=all`): 301 of 365 steps agree with Wasmtime for each, and the C and the Python agree on 365 of 365**. **Not compared with a real host:** sockets, terminals, a real stdin, and Windows, macOS, ARM64 and 32-bit against Wasmtime (they build and run the C drivers against the Python twin in the CI). The comparison with Wasmtime does not run in the CI (it needs Wasmtime, `wasm-tools` and the Rust target); the programs that are compared with Wasmtime's own WASI there are the ones of `tests/neutral/`.
- The deliberate differences from the letter of the WIT are listed in `host_scope.md`; each should be kept on purpose or removed.

**The Windows runner, 2026-10-27.** The job skipped 49 tests, 44 of them because the C drivers were assumed POSIX only; they run now (MinGW `gcc`, `tests/cbuild.py` adds the libraries): the C twins of `parity_surface`, `p1_over_p2`, `p1_errno`, `p1_headers`, `clocks`, `io`, `random` and `cli`, and the Python-only tests that had been skipped with them. Running them found a real difference: on Windows the Python `SystemFilesystem.open_directory` did not check that a preopen exists or is a directory; both twins do now. What still does not run on Windows, and why: `test_wasi_p1_core.py` FIFO (no FIFO on Windows), `test_wasi_p1_core.py` native poll (no `select.poll`), `test_wasi_p2_cli.py` scenario `fd` and its Python twin (the driver makes pipes with `pipe()`), `test_wasi_p2_filesystem.py:526` (the mapping of errno of the C library; Windows has its own numbers). The test of the errno of 0.1 leaves out the numbers that Python's `errno` has as Winsock numbers on Windows.

**MSVC.** The job `msvc` compiles every header now (it had only the headers of 0.1, for no reason of the headers): the one finding was a `size_t` given to `connect()`. See `host_scope.md`, "Known limits". Since 2026-10-28 the C drivers of the tests are also built with `cl` (`/std:c11 /W4 /WX`) and run by the job `msvc-run` (128 tests passed, 5 skipped for what Windows does not have; see `host_scope.md`, "Known limits"); the findings were `#pragma GCC`, a 64-bit table given to 32-bit parameters, `inp` (a name of `conio.h`) and two offsets cl could not prove initialised.

## 4. Packaging (done 2026-10-28)

The name `fusedwasi` is taken on PyPI by the owner and ready for a publication, so the first release is a pre-release (`0.1.0a1`), which users install with `--pre` instead of a commit. The build is `setuptools` + `setuptools-scm`, as in the other two packages: **the version is the git tag** (`v0.1.0a1` is `0.1.0a1`; a build-only run takes `SETUPTOOLS_SCM_PRETEND_VERSION`). The wheel carries the Python twin, the C headers, `get_include()`, the tables of signatures, `public_api.json` and `py.typed`, and the licences (`LICENSE` and the licence of the WASI specification the tables are made from); the sdist carries all of that plus `CMakeLists.txt`, `fusedwasi-config.cmake.in`, the tests and the docs (the CMake install is for a source tree or the sdist; the wheel has no CMake files, and README says so). Checked: `tests/test_package.py` (headers in the package; `cmake --install` and a project that does `find_package(fusedwasi)`), and the smoke step of `publish.yml` (a clean environment, the tables, a C program compiled against `python -m fusedwasi`). `publish.yml` is the one of the other packages: tag `v*`, the tag must equal the version that was built, PyPI by trusted publisher (environment `pypi`, no token), `skip-existing`, a GitHub release (a pre-release for `a/b/rc/dev`). **Before the first push of a tag:** the trusted publisher of PyPI for this repository and the environment `pypi` must exist (settings of PyPI and of the repository: only the owner can do it).

## 5. The order

1. The state and the guest (done, `3c3924b`, `b4aa2db`): the model of `design_model.md`.
2. The official wasi-testsuite (0.1) and the neutral user in Python (the twin over `wasmtime-py`) in the CI of fusedwasi. This is the net under step 3 and the first half of the proof of neutrality. **Written** (`tests/neutral/`, job `python-wasmtime` of `neutral.yml`; 72 tests of the wasi-testsuite pass locally; see `design_model.md`, section 11).
3. 0.1 over 0.2 (`design_model.md`, section 4). **Done** (stage B: one state and one guest for both families, the descriptors of 0.1 are resources of the table of 0.2, the functions of 0.1 call the operations of 0.2; the 72 tests of the wasi-testsuite, the three neutral users and the C/Python parity tests pass; see `design_model.md`, section 4 and `host_scope.md`, "Changes of 0.1 that 0.2 forced").
4. The C user over an engine that is not `wasm2c` (`wasm3` first; a hand-made guest memory as the fallback), the second half of the proof of neutrality (`design_model.md`, section 11). **Written** (`tests/neutral/c_wasm3/`, job `c-wasm3` of `neutral.yml`; passes locally on Linux). A third, small Python user over `pywasm3` is in `tests/neutral/` (job `python-wasm3`).
5. Public/private marks, the dead names, the gaps of section 3 closed or deferred in writing. **Done 2026-10-27** (`design_model.md` section 5; `public_api.md`; `private_names.md`; `tests/test_public_api.py`). The public documents (`README.md`, the headers, the docstrings) say nothing about how a particular user works.
6. The remaining checks. **Done 2026-10-28:** Windows (MinGW; MSVC builds and runs the C drivers and the wasm3 user), macOS, ARM64 Linux and the C drivers as 32-bit programs in the CI (`c-checks.yml`); **Windows ARM64 since 2026-11-05** (job `msvc-run-arm64`: the C drivers built with the ARM64 `cl`, 145 passed, 5 skipped for what Windows does not have); the package test (section 4), with a wheel built without git. The 32-bit run found a real defect (the UDP receive read at most `sizeof` a pointer of a datagram), fixed.
7. Tag and publish `0.1.0a1` (the owner sets the tag `v0.1.0a1`; `publish.yml` checks that it equals the built version). A stable `0.1.0` waits for use, not for a feature of a user: the states are opaque across artifacts (the layout does not cross), so no user's versioned record is a condition.
