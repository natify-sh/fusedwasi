# S0006: `tls_wrap` in the Python twin (a setting of TLS for `wasi:http`)

**Status:** deferred 2026-11-05: it is not needed for parity with Wasmtime and Spin, which do not have it (S0013, sections 2 and 7). Kept as the record of what it would take.

## 1. The problem

The Python twin uses `ssl.create_default_context()`, the system trust store, and has no setting; this is **deliberate** (2026-11-05, S0001 section 3.3) and pinned by `test_python_tls_is_ssl_with_the_system_store_and_has_no_setting` **[read]**. A Python embedder who needs a corporate CA, a pinned certificate or a client certificate cannot do it except by replacing the whole transport with `http_send`.

## 2. Options

* **A. Nothing (today).** `http_send` is the way; it replaces the transport and so the TLS with it.
* **B. A `tls_wrap(sock, hostname)` in the state**: a callable that gets the connected socket and the host name and returns a wrapped socket (or raises). It is the same shape as the C hook (`connect` over a descriptor that is connected) in a Python way, and it leaves HTTP in the library. Checks of the chain and of the name stay in the callable, as the contract of the C hook says (the hook must verify; the library cannot enforce it) **[read: `docs/tls_hook.md`, section 2]**.
* **C. An `ssl.SSLContext` in the state.** Smaller than B, and covers the corporate CA, pinning and client certificates by the standard way.

## 3. What decides it

Parity: the C twin has the hook, the Python twin has nothing; the difference is documented as deliberate, and this spec would remove the reason for it. The feature matrix (`docs/features.json`, `tlsHook`) says the difference both sides; it must change in the same commit as any code.

## 4. Proposal (a draft)

C first (an `SSLContext` is what a Python user already has and the check of the name stays in `ssl`); B only if someone needs a non-`ssl` TLS. Either is small and has to be tested against the same TLS server as the reference hook (`tests/test_tls_reference.py` already has one).
