# S0010: Android in the CI: what the job is, and what it is not (state of 2026-11-05)

**Status:** draft (a record of the state and a proposal; the owner decided on 2026-11-05 that the job is **not required** for a merge, and the rest is open). The facts are marked as in the other documents of `docs/`.

## 1. What exists

The job `android` of `.github/workflows/test.yml` (name "the Python twin in an Android app (emulator, x86_64)") **[read]**: the python.org Android package 3.14.10 (pinned by SHA-256), the testbed app of CPython, a Gradle-managed emulator with KVM, Android 15, SELinux `untrusted_app`. The tests are the files that `tools/android_check.py` lists: the Python twin, with the tests that build C skipped (an app has no C compiler). It is the recipe of the repository `natify-sh/waboros` **[read: its `ci.yml`, job `android`]**.

## 2. The decision of the owner

The job is **not required for a merge**. At the time of writing the branch `main` has no protection and no ruleset, so no check is required at all **[run: `branches/main/protection` answers 404 "Branch not protected", `rulesets` is empty]**; the job is informative: it shows red in a pull request and nobody is blocked by it. If a protection is turned on later, this job is **not** to be added to the required checks without a new decision.

## 3. Why not required (the reasons I gave, for the record)

* it depends on downloads that the repository does not control: the SDK and the system image through Gradle, the package of python.org;
* two runs say nothing of its stability;
* it runs 50 of 146 tests of the files that it lists, and what it finds is most often a property of Android (the hard link) and not a regression;
* it is the longest job of the matrix (about 4 minutes on the first run **[run]**).

## 4. Open

* **What it does not cover:** the C twin **in this repository's tests** (no compiler in an app; building the C drivers with the NDK and running them in the app is a larger piece of work and is **not started**). The C headers are built with the NDK and run in an emulator by a user: `natify-sh/py-wasmext`, branch `dev` (commit `41b6d18`), depends on `fusedwasi>=0.1.0b1`, includes `fusedwasi/p1` and `fusedwasi/p2` headers in the C it generates, and its job `Example wheels` builds the CoreMark wheel for Android (NDK 27, Python 3.13) and runs it on an x86-64 emulator with KVM (arm64-v8a: built, not run) **[read: its `pyproject.toml`, `_binding.py`, `example-wheels.yml`, `docs/FEATURES.md`; not run here]**. That covers a build and a smoke run of the published `0.1.0b1`, not the C drivers of this repository, not the current tree, and not which WASI calls CoreMark makes **[not checked]**, arm64 (GitHub has no arm64 runner that can run the emulator), other versions of Android (only the newest, `maxVersion`).
* **The code of the hard link:** **closed 2026-11-05.** The system answers `EACCES`, and the host answers `access`; this is pinned by `test_a_refused_hard_link_gives_the_error_of_the_system`, which simulates the refusal (so it runs on every system, not only where one is refused). The C twin is pinned the same way by `test_a_refused_hard_link_gives_the_same_code_in_c`. Not seen: the job on a real Android with that test.
* **Stability:** how often the job fails without a cause in the code is not known. A line in `docs/release_checklist.md` (section 6) is where the count can be kept.

## 5. Proposal (a draft)

Keep the job as it is, informative. After some weeks, if it has not failed without a cause in the code, say so here and let the owner decide again whether it is worth a place among the required checks. Do not widen it (the NDK, arm64) before a user of the library on Android is known.

## 7. The C twin on Android: options, deferred (2026-11-05)

Nothing of this is built, and nothing is to be built until the owner says so or a user of the C headers on Android asks. The levels, from the cheapest, with what each shows and does not show **[not run: these are estimates from reading the CI and the tests]**:

1. **Compile only, with the NDK, no emulator.** `-fsyntax-only` or `-c` of the headers (and of the C drivers) with the NDK clang, as the MSVC job of `c-checks.yml` does. A minute on a plain runner, no KVM, no Gradle. It finds what bionic lacks or declares differently (a function, a constant, a header); it does not run anything, so it shows nothing about behaviour. Whether the runner image has an NDK is **[not checked]** (the job `android` uses the SDK and an emulator).
2. **One driver through `adb shell` on the emulator that the job `android` already starts.** Build a driver with the NDK, push it and a tree of files, run it, pull the output, compare with the Python twin. The tests that compare the twins (`test_c_and_python_agree`) start the driver as a process of the host and read its output, so `tests/cbuild.py` and the tests would need a notion of "where it runs"; one driver (the filesystem one) is the way to learn the cost before doing the rest. The process runs as the `shell` user and not as `untrusted_app`, so the SELinux of an app (a refused `link`, `/proc`) is **not** what it sees.
3. **The drivers inside the testbed app.** The only way to see the SELinux of an app for the C twin. The largest piece of work; not started.

What exists meanwhile: the Python twin runs in the app (job `android`, section 1), and a user builds and smoke-runs the released headers on an x86-64 emulator (section 4). Written in `host_scope.md`.
