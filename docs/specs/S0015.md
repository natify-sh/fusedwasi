# S0015: What the confinement of paths promises in `wasi:filesystem` and WASI 0.1, and what it does not

**Status:** draft (a proposal; nothing is decided and nothing is changed). Written 2026-11-05 from a note of the `wasmhost` project (its backlog item B-503: "a sandbox through `openat` with `dir_fd`, to remove the gap between checking the path and opening it"), which is passed on as information and not as a request for a fix on a schedule. The facts are marked as in the other documents of `docs/`: **[read]** read in the code, **[run]** run, **[not checked]** not looked at or not run.

## 1. The question

The docstring of `wasi_p2_filesystem.py` says that the paths are walked by name and that "a race with another process that changes the tree under the walk is not closed", and that on Windows "the check and the use are two steps". A host that gives a guest a preopen and shares that folder with another process (or another guest) asks: **is the race a way out of the preopen?** And what must a host say to its users about it.

## 2. What the code does

**POSIX, Python twin [read: `_walk` in `wasi_p2_filesystem.py`].**

* A path is cut into names. Each name is used **alone**: a directory on the way is opened with `os.open(name, O_RDONLY | O_DIRECTORY | O_NOFOLLOW, dir_fd=<the directory already held>)`. The kernel is never given a path with more than one name, so it resolves no `..` and no link by itself.
* `..` is **the walk's own**: the walk keeps a stack of the descriptors it opened, `..` pops it, and a `..` with only the base left is `not-permitted`. A directory that is renamed away under the walk does not change what `..` means.
* A link is read (`readlink`) and its target is put in front of the rest of the path; the walk then goes on by the same rule. An absolute target is `not-permitted`; at most 40 links, then `loop`.
* The last name is given to a call that does not follow a link at the end (`O_NOFOLLOW`, `AT_SYMLINK_NOFOLLOW`, `unlinkat`, `renameat`, `linkat`).

**POSIX, C twin [read, not run for this document].** `fusedwasi_p2__walk_path_with` has the same shape (an array of the descriptors, `depth`, `openat` with `O_NOFOLLOW`).

**Windows, both twins [read: the docstring and `wasi_p2_fs_win32.h`].** There is no `dir_fd` and a directory cannot be opened as a file. A directory descriptor is a path; the same walk goes below that path by name, and the check and the use are two steps. A junction can be made without a privilege; a symbolic link needs one.

## 3. What was run

A script (a temporary tree, only reads) tried to leave the preopen on **Linux, the Python twin**, for 8 seconds, with four threads that kept changing the tree under the guest's `open_at` + `read`: a link swapped atomically between `real`, `../outside`, `/etc`, `real/../../outside` and `sub/../../outside`; a directory swapped in place of a link to the outside and back; the directory the guest was inside moved away and back. The guest opened nine paths over and over (`swap/secret`, `swap/sub/secret`, `dirswap/secret`, `swap/../secret`, `real/../../outside/secret`, `dirswap/../../top`, ...). **[run]** 82 602 opens, 126 670 changes of the tree, **0 escapes** (the guest read `INSIDE` 10 392 times; all the rest were `no-entry`, `not-permitted` or `not-directory`).

This is **not a proof**: one run, one system, threads under the GIL, the Python twin only.

## 4. What follows

1. **On POSIX the walk is not open to an escape by a race**, by its construction: the kernel resolves one name at a time against a descriptor the walk holds, with no `..` and no link in it, and `..` is the walk's. What a change under the walk can do is to change **which entry a name is** (the ordinary meaning of a race on any filesystem), not to lead out of the base. The sentence of the docstring is wider than that and should say what is true.
2. **What a preopen does not promise on POSIX:** protection from what the administrator built into the tree (a bind mount, a hard link to a file outside, a directory that is a mount point), and from **a link that the guest itself plants**. The last one is a different problem from the race: in WASI 0.2 `symlink-at` refuses only an absolute target and `NUL`, so the guest can make `lnk -> ../outside` **[read: `wasi_filesystem_types_descriptor_symlink_at`; run: the operation `symlink_at` made `../outside` and `sub/../../outside`]**. Our own walk never follows it out, but **another process that reads the same folder does**. WASI 0.1 `path_symlink` refuses a link that leads out **[read]**, so the two families differ.
3. **On Windows the race is real**: the check and the open are two steps on a path, and a local process with the right to write in the folder can put a junction in place of a directory between them. A check after the open (`GetFinalPathNameByHandle` of the handle against the preopen) narrows the window and does not close it. To close it the walk has to go **by handle** (each name opened relative to the handle of the directory before it, with the reparse points not followed), which is what the kernel's `NtCreateFile` with a `RootDirectory` does and what the standard library of Python does not give.
4. **What the other hosts do [read, 2026-11-05]:** Wasmtime (`cap-primitives`): `openat2(RESOLVE_BENEATH)` on Linux and `O_RESOLVE_BENEATH` on FreeBSD, a walk by hand elsewhere (the same as ours); uvwasi: a normalisation of the path as text and a check that it starts with the base, which is weaker than a walk by descriptors.

## 6. Proposal (a draft)

A now (words that say what is true, for POSIX and for Windows), B with it, and a decision on F. C and D only if a user asks; E is the real answer for Windows and is a piece of work of its own, and until it is done the README should say that **on Windows a preopen is not a barrier against another process that can change the folder**.

## 7. For the owner to decide

1. Is a process that can change the shared folder in the threat model? (On POSIX it cannot lead out; on Windows it can.)
2. F: refuse a link that leads out in `symlink-at` of 0.2? It protects a host that shares the folder with a process that follows links; it takes away something a guest could do.
3. Is the text of section 4, item 1 what the library is willing to promise on POSIX? It rests on the construction of the walk and on one run, not on a proof, and **the C twin was only read**.
4. Does the Windows side get a piece of work (E), or only the words?

## 8. Not checked

The C twin was read and not run for this; Windows was not run at all; macOS and the BSDs were not run; the run is one run of 8 seconds; the behaviour of Wasmtime for a guest that makes a link which leads out (option F) was not read.
