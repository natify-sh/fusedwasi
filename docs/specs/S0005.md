# S0005: HTTP/2 for `wasi:http`

**Status:** draft (a proposal; nothing is decided). Written 2026-11-05 so that an open question of `docs/release_checklist.md` (section 6) is not lost. The facts are marked as in the other documents of `docs/`.

## 1. The problem

The transport speaks HTTP/1.1 only, one connection for each request **[run: `test_http_is_http_1_1_with_one_connection_for_each_request`, and `_in_c`]**. A server that insists on HTTP/2 is a rare case (most servers still answer HTTP/1.1) **[not checked: from memory]**.

## 2. What it would need

* TLS with ALPN (S0001 does not give the hook an ALPN list; S0002 lists ALPN as not a goal). The hook would need a way to ask for `h2` and to say what was agreed.
* HPACK, the frames, the flow control, the streams of one connection: a second protocol implementation in C **and** in Python (the Python twin does it by `http.client`, which has no HTTP/2).
* The rule of the library: header-only, no dependencies. A library for HTTP/2 (nghttp2) would be a dependency; writing it is a large piece of code **[not checked: an estimate]**.

## 3. Options

* **A. Not planned; the limit is documented (today).**
* **B. Through the transport hook only:** an embedder who needs HTTP/2 sets `http_send` with its own client (libcurl, nghttp2). Costs the library nothing; costs the embedder the work.
* **C. In the library.** Only after streaming (S0003), since HTTP/2 without streaming of bodies gives little.

## 4. Proposal (a draft)

B now, written in `host_scope.md` as the way; C is not started before S0003 and a real need.

## 5. For the owner to decide

1. Is B enough as the final answer to "HTTP/2"?
2. If C: is a dependency allowed for it, in an optional build as S0002 would be?
