# S0001: A TLS hook for the transport of `wasi:http`, in C and in Python

**Status:** accepted 2026-11-05 (the owner accepted the five decisions of section 8 as proposed). Implementation is in the steps of section 9; each step says in the log when it is done. The earlier form of this spec, a TLS backend that the library owns over Mbed TLS, is [S0002](S0002.md), deferred.

## 1. The problem

`https` in the C twin is `internal-error` ("https needs a transport of the embedder ... this host has no TLS") unless the embedder sets `state->http_send` **[read: `wasi_p2_http.h`, `fusedwasi_p2_http_default_send`; pinned by `test_http_the_c_has_no_tls`]**. `http_send` replaces the **whole** transport: an embedder that only wants TLS must write an HTTP/1.1 client too. The Python twin has TLS through `ssl`, with the system trust store and no way to change it **[read: `wasi_p2_http.py`, `ssl.create_default_context()`]**. `host_scope.md` ("Known limits") records this as a deferred limit.

## 2. Goals and not goals

Goals:

1. A C embedder gets `https` by giving **only the TLS**: a few functions over the TLS library it already has (Mbed TLS, OpenSSL, wolfSSL, Schannel, ...). The library keeps the connection, the HTTP/1.1 request and answer, the timeouts of each phase, the limits of the bodies and the errors.
2. **The library has no TLS code and no TLS dependency.** The headers, the wheel and the sdist are the same as without this spec, apart from the hook.
3. The two twins have the **same hook, the same errors** for a guest, and the same output for the same request on the same server.
4. The hook is **tested** in CI with a real TLS library, so that the instructions for it do not rot.

Not goals: choosing or bundling a TLS library (S0002, if ever), the trust store of the system, HTTP/2, ALPN, client certificates, a TLS server (the `incoming-handler` side stays the embedder's).

## 3. The design

### 3.1 One layer under the transport

The transport of `wasi_p2_http.h` reads and writes the file descriptor directly, with the timeouts of the request. It gets a small layer, `fusedwasi_p2__http_conn` (a descriptor and an optional session of the hook) with `read`, `write` and `close`, and the code that builds the request and reads the answer uses it. For `http` the layer calls `recv` and `send` as now and the bytes on the wire do not change. For `https` it calls the hook.

### 3.2 The hook in C

A table of four functions, set on the state like `http_send` is:

```c
typedef struct fusedwasi_p2_tls_error { int kind; const char *message; } fusedwasi_p2_tls_error;
/* kind: FUSEDWASI_P2_TLS_CERTIFICATE, _PROTOCOL, _TIMEOUT, _TERMINATED, _OTHER; message: NULL or a text that the library copies */

typedef struct fusedwasi_p2_tls_ops {
    /* `fd` is connected. Handshake, verify the chain and the host name, within `timeout_ms`. Returns a session, or NULL with `err` set. */
    void *(*connect)(struct fusedwasi_p2_state *s, int fd, const char *host, int timeout_ms, fusedwasi_p2_tls_error *err);
    /* >0 bytes read; 0 the peer closed the session in order; <0 failure with `err` set. Waits at most `timeout_ms`; a timeout is kind TIMEOUT. */
    int (*read)(void *session, uint8_t *buf, size_t n, int timeout_ms, fusedwasi_p2_tls_error *err);
    int (*write)(void *session, const uint8_t *buf, size_t n, int timeout_ms, fusedwasi_p2_tls_error *err);
    void (*close)(void *session); /* sends the close notification if it can, and frees the session; the library closes `fd` after it */
} fusedwasi_p2_tls_ops;
```

and a field `const fusedwasi_p2_tls_ops *tls` of the state. These names are a proposal. The state calls the functions for one request at a time, but **different requests may run at the same time** (as the plain transport does), so a session must not share mutable state with another.

**The descriptor** that `connect` is given is connected and in blocking mode; the hook may change the mode, and the library only closes it after `close`.

**The hook owns the waiting.** A TLS library may hold bytes that it has decrypted, so polling the descriptor is not enough: `read` and `write` get the time they may take and do the `poll` themselves. `host` is the authority of the request without the port; an IP address is given as text.

**Precedence.** `http_send` set: it replaces everything, `tls` is not looked at. `tls` set: used for `https`. Neither: `https` is the `internal-error` of today.

### 3.3 The hook in Python

`State(tls_wrap=f)` (and `Host`), where `f(sock, hostname) -> sock2` takes the connected socket and gives a socket-like object with `settimeout`, `recv`, `sendall` and `close`. `ssl.SSLContext.wrap_socket(sock, server_hostname=hostname)` is exactly that. With `tls_wrap` unset, Python keeps what it does now: `ssl.create_default_context()`, the system store.

That is the **one deliberate difference** of the twins: Python has a system store of its own, and C has no TLS at all until the embedder gives one. A test and a guest that give a hook to both see the same behaviour.

### 3.4 The contract, and what the library does not guarantee

The hook **must**: verify the certificate chain and the host name; offer TLS 1.2 or later; end a session with a close notification when it can; report a failure as one of the kinds. The library **cannot check this**: an embedder can write a hook that does not verify. The documents say it plainly (`docs/tls_hook.md`, section 5). The embedder who wants another policy is free to, as with `http_send`.

### 3.5 The errors

The twins map the failure to the same `error-code` cases:

| What the hook reports | `error-code` |
| --- | --- |
| `CERTIFICATE` (Python `ssl.SSLCertVerificationError`) | `TLS-certificate-error` |
| `PROTOCOL` (any other `ssl.SSLError`) | `TLS-protocol-error` |
| `TIMEOUT` (`TimeoutError`) | `connection-timeout` for `connect`; `connection-read-timeout` and `connection-write-timeout` for `read` and `write`, as the plain path |
| `TERMINATED` (a closed or reset connection: `ConnectionError`, `BrokenPipeError`) | `connection-terminated` |
| `OTHER`, and a session that ends before the answer is whole | `internal-error` with the message |

`message` goes into the payload of `TLS-certificate-error` and `TLS-protocol-error` where the case has a text. `TLS-alert-received` is **not** used in this version in either twin: Python's `ssl` and the C libraries do not give the alert in one form, and an answer that differs between the twins is a bug. It stays in the table of the cases, unused; `host_scope.md` says so.

### 3.6 Public names

The struct, the kinds, the table and the state field are public (unstable in the alpha, as `wasi:http` is), listed in `public_api.json`; `public_api.md` is made from it again.

## 4. The instructions

`docs/tls_hook.md` (a new file, written with the code): the contract of 3.4; the hook over Mbed TLS **in full**, the one that CI builds and runs (so it is the one that is known to work); the Python hook; and a short note for OpenSSL, wolfSSL and Schannel (what to call for `connect`, `read`, `write`, `close`), marked **[not checked]** until someone runs them. The trust anchors, the versions and the suites are the embedder's, and the file says where in the hook they are set.

## 5. The tests

1. **The mapping, without any TLS library** (runs in every job of the CI, on every system): a fake hook, in C and in Python, that returns each kind and a timeout, a short read, a read after the close, and a failure in `connect`; the twins give the same `error-code` and the same output (a scenario run in both and compared, as the others are). Also: `tls` unset gives the `internal-error` of today; `http_send` set takes precedence; a request over `http` is not touched.
2. **The reference hook over a real library** (Mbed TLS), against a local TLS server of the test (Python `ssl`) with a throwaway CA and a server certificate made at the time of the test (the `openssl` command): a request over TLS, the C and the Python give the same status, headers and body; the host name does not match; the CA is not trusted; a server that speaks plain HTTP on the TLS port; a server that offers only an old TLS version; a body over one TLS record (more than 16 KiB); a body that ends with the closing of the connection; an IP address as the authority, with the address in the certificate; the timeouts of the handshake and of the answer. No test uses the internet.

The reference hook lives in `tests/tls_mbedtls/`, **its own CMake project** that takes Mbed TLS with `FetchContent_MakeAvailable(mbedtls)` (the source pinned by an archive URL and `URL_HASH SHA256=...`; static; programs and tests off; a trimmed configuration of the kind that [S0002](S0002.md) measured) and builds a driver that the tests of 2 run. Mbed TLS is never part of the library, of the wheel or of the sdist (the sdist carries that `CMakeLists.txt` as it carries the other files of `tests/`, and not Mbed TLS). A test that needs it is skipped where `cmake`, the compiler or the network is not there, and the job that is meant to run it fails on that skip (`FUSEDWASI_ALLOWED_SKIPS`, as the others do).

## 6. The CI

* The mapping tests (5.1) run in **every** existing job, with no new dependency: they are part of the suite.
* One new job on Ubuntu runs 5.2: it fetches Mbed TLS with CMake (the archive is cached by the pin) and builds the reference driver. macOS, Windows (MSVC, at `/W4 /WX`), Windows ARM64, the sanitizers and the 32-bit job are added one at a time after it is green; the 32-bit job may leave 5.2 out if a 32-bit Mbed TLS is too costly, and then says so.
* `host_scope.md` and `release_checklist.md` move the limit "`https` in C" from deferred to "fixed with a hook"; `README.md` (the feature list says "TLS in Python only") says what an embedder does.

## 7. Risks that are not decided

* **The descriptor mode (read 2026-11-05, step 1).** The transport connects the socket **non-blocking** and, once it is connected, sets it back to **blocking**; then it waits with `poll` (for the time of the phase) before each `recv` and `send` **[read: `fusedwasi_p2__http_connect`, `fusedwasi_p2__http_conn_read` and `_write`]**. So the descriptor that `connect` of the hook is given is connected and **blocking**. The hook may change the mode during its session (a hook that does its own waiting will often make it non-blocking), and the library does nothing else with the descriptor than close it after `close`. The contract of 3.2 says so.
* **Thread safety** of a hook that keeps a global state (a random generator of Mbed TLS, for one): the contract says that a session is not shared, and the reference hook makes a generator for each session.
* **The wall clock** for the validity of a certificate comes from the library that the embedder uses, not from the `clock` of the state of the host. A guest with a fake clock still sees real time in that check. It should be written down.
* **Mbed TLS 4.0** splits its crypto into TF-PSA-Crypto and changes the API; the reference hook is for 3.6 and a move to 4 is a change of that one file.
* A security fix of the TLS library is the embedder's to take. The reference hook pins one version, in one line.

## 8. What the owner has to decide

1. **The shape:** a table of four functions in C (`state->tls`), a function `tls_wrap(sock, hostname)` in Python, the hook owning the waiting, and a small set of error kinds. (Proposed.)
2. **The contract is a contract, not a check:** the hook must verify, the library cannot enforce it, and the documents say so. (Proposed.)
3. **`TLS-alert-received` is not used** in either twin in this version. (Proposed.)
4. **The reference hook is Mbed TLS 3.6, in the tests only**, fetched by CMake in a project of its own, pinned by hash. It is also the one the instructions show in full. (Proposed.)
5. **S0002 stays deferred**: a backend that the library owns is done only if the hook and the instructions are not enough. (Proposed.)
