# S0001: Optional TLS for the C transport of `wasi:http`, over Mbed TLS

**Status:** draft. Written 2026-11-05 after a discussion with the owner; nothing here is built. The decisions that the owner still has to confirm are in section 9.

## 1. The problem

`https` in the C twin is `internal-error` ("https needs a transport of the embedder ... this host has no TLS") unless the embedder sets `state->http_send` **[read: `wasi_p2_http.h`, `fusedwasi_p2_http_default_send`; pinned by `test_http_the_c_has_no_tls`]**. The Python twin has TLS through `ssl`, with the system trust store **[read: `wasi_p2_http.py`, `ssl.create_default_context()`]**. So a guest that makes an `https` request runs in Python and needs a transport of its own in C. The two twins differ, and `host_scope.md` ("Known limits") says so as a deferred limit.

## 2. Goals

1. A C embedder can get `https` from the library **without writing a transport**, by choosing to build with TLS.
2. TLS is **optional**: the library stays header-only and free of dependencies by default; a build that does not ask for TLS is byte for byte the build of today.
3. The check of the certificate and of the host name is **always on**. There is no switch that turns it off.
4. The two twins give a guest **the same answer** for the same failure (the same `error-code` case), and the same output for the same request on the same server.

## 3. Not goals

* HTTP/2, ALPN, client certificates, session resumption, a TLS server (the `incoming-handler` side stays the embedder's).
* The trust store of the system (Keychain of macOS, the certificate store of Windows, `/etc/ssl` paths). The embedder gives the trust anchors. A later spec may add the system stores.
* Bundling Mbed TLS in the Python wheel. The wheel carries the optional header, as it carries every header; it carries no Mbed TLS.
* A second TLS library. If the owner wants one later, it is another spec with its own header.

## 4. The choice of the library

**Mbed TLS**, the branch 3.6 (LTS) **[not checked: that 3.6 is the LTS line now, and the exact last tag; to be read at the time of the work]**, pinned (section 6).

Why: it is a C library with no required system dependency, it builds with CMake, its size can be cut with its configuration, and a project of the same kind uses it: MicroPython's `ssl` is `extmod/modtls_mbedtls.c`, compiled only under `MICROPY_PY_SSL && MICROPY_SSL_MBEDTLS`; a client is `CERT_REQUIRED` by default and needs the host name for that; the library loads **no** default trust store and the program gives the CAs (`load_verify_locations`, PEM or DER) **[read, 2026-11-05: https://raw.githubusercontent.com/micropython/micropython/master/extmod/modtls_mbedtls.c]**. This spec takes the same shape.

Why not the others **[not checked: from memory]**: BearSSL is small and MIT but TLS 1.2 only and little maintained; wolfSSL is GPL or commercial, which does not go with an MIT library; OpenSSL is large and depends on the system; the APIs of the systems (Schannel, SecureTransport) are three backends instead of one.

Licence **[not checked]**: Mbed TLS is dual licensed (Apache-2.0 or GPL-2.0-or-later). fusedwasi is MIT. Because the header is optional and the embedder links Mbed TLS, nothing of Mbed TLS enters the wheel or the MIT licence of the library; this has to be confirmed against the licence text before a release that offers the build.

## 5. The design

### 5.1 One optional header, one macro

A new header, `wasi_p2_http_tls_mbedtls.h`, in `src/fusedwasi/include/fusedwasi/p2/`. `wasi_p2_http.h` includes it **only** when the embedder has defined `FUSEDWASI_P2_HTTP_TLS_MBEDTLS` before the include. Without the macro nothing changes: `https` is the `internal-error` of today, and `http_send` still replaces the whole transport.

### 5.2 A connection that is a socket or a TLS session

The transport of `wasi_p2_http.h` reads and writes the file descriptor directly (`recv`, `send`, `poll` with the timeouts of the request). It gets a small layer, `fusedwasi_p2__http_conn` (a descriptor and an optional TLS session) with `read`, `write` and `close`, and the code that builds the request and reads the answer uses it. For `http` the layer calls `recv` and `send` as now; the bytes on the wire do not change. For `https` it calls `mbedtls_ssl_read` and `mbedtls_ssl_write`, with a BIO that uses the same `poll` and the same three timeouts (connect, first byte, between bytes) as the plain path, so that `WANT_READ` and `WANT_WRITE` wait in the same way.

### 5.3 Trust and verification

The state of the host gets three fields: `tls_ca_file` (a path to a PEM bundle), `tls_ca_pem` and `tls_ca_pem_len` (the bundle in memory). The embedder sets one of them.

* The verify mode is required, always (`MBEDTLS_SSL_VERIFY_REQUIRED`). The server name is set for SNI and for the check (`mbedtls_ssl_set_hostname`) from the authority of the request, without the port. An IP address in the authority is checked against the IP addresses of the certificate.
* With no trust anchor given, the request fails with `TLS-certificate-error` and the text "no trust anchors: set `tls_ca_file` or `tls_ca_pem` of the state". It never falls back to no check. An embedder that really wants another policy writes `http_send`.
* The lowest protocol version is TLS 1.2. The suites are those of the configuration of the build.
* A context is made for each request and freed at its end; there is no global state, so the transport stays safe to call from several threads, as the plain one is.

### 5.4 The errors

The two twins map the failures to the same `error-code` cases:

| What happened | `error-code` |
| --- | --- |
| the certificate or the host name does not verify (Mbed TLS `MBEDTLS_ERR_X509_CERT_VERIFY_FAILED`; Python `ssl.SSLCertVerificationError`), no trust anchor in C | `TLS-certificate-error` |
| any other failure of the handshake or of the records, a server that does not speak TLS, a version that is too old | `TLS-protocol-error` |
| a timeout of a phase | the same cases as the plain path (`connection-timeout`, `connection-read-timeout`, `connection-write-timeout`) |
| the peer closes before the handshake ends | `connection-terminated` |

`TLS-alert-received` is **not** used in this version, in either twin: Python's `ssl` does not give the alert in a form that is the same as Mbed TLS's, and an answer that differs between the twins is a bug. It stays in the table of the cases, unused, and `host_scope.md` says so.

### 5.5 The Python twin

Python has TLS already. For parity it needs the same setting of the trust anchors: `State(tls_ca_file=..., tls_ca_pem=...)`. When one is given, the context loads **only** those anchors, as the C does. When none is given, Python keeps the system store of `ssl.create_default_context()`.

That is the **one deliberate difference** of the twins: Python has a system store for free, and C has none. It is written in `host_scope.md`. A test and a guest that give the anchors explicitly see the same behaviour in both.

The way the setting reaches `default_send` (it has no `state` today) is left to the work, but it is per state and not a global.

## 6. The build

The headers stay a header-only `INTERFACE` target, `fusedwasi::headers`, with no dependency. TLS is a second target.

* **A component of the package.** `find_package(fusedwasi REQUIRED COMPONENTS tls)` loads a CMake module, `cmake/FusedwasiTls.cmake` (installed with the package; `fusedwasi-config.cmake` includes it for the component `tls`), which defines `fusedwasi::tls_mbedtls`: an `INTERFACE` target that sets `FUSEDWASI_P2_HTTP_TLS_MBEDTLS=1` and links `MbedTLS::mbedtls` (with `mbedx509` and `mbedcrypto`), static. A project that takes fusedwasi with `add_subdirectory` or `FetchContent` gets the same target from the same module. Without the component nothing about TLS is loaded.
* **Where Mbed TLS comes from**, one variable, `FUSEDWASI_TLS_MBEDTLS_SOURCE`:
  * `AUTO` (the default): `find_package(MbedTLS 3.6)` first; if it is not found, fetch it;
  * `SYSTEM`: only find it, and an error if it is not found. For an embedder that has its own Mbed TLS (a second copy in one program gives duplicate symbols);
  * `FETCH`: always fetch.
  Fetching is **`FetchContent_MakeAvailable(mbedtls)`** in the project of the embedder, at its configure time, with the source pinned by an archive URL and `URL_HASH SHA256=...` (not by a git tag: a tag can move, a hash cannot), its programs and tests off (`ENABLE_PROGRAMS`, `ENABLE_TESTING` off) and its static libraries on. The pin is a default that the embedder may replace: `FUSEDWASI_MBEDTLS_URL` and `FUSEDWASI_MBEDTLS_SHA256`. Offline builds use `FETCHCONTENT_SOURCE_DIR_MBEDTLS` or `FETCHCONTENT_FULLY_DISCONNECTED`. The module needs CMake 3.14 (`FetchContent_MakeAvailable`); the rest of the package stays at 3.13, and the module says so in an error when the version is older.
* **Nothing about Mbed TLS is exported by the installed package.** The package carries the module and the header; the fetching happens in the project that asks for the component, so `fusedwasi::headers` never links Mbed TLS and the package stays light.
* In this repository an option, `FUSEDWASI_TLS` (off by default), builds the same target for the tests and the CI.
* **Not checked:** that the `MbedTLSConfig.cmake` of the distribution packages gives the targets `MbedTLS::mbedtls`, `MbedTLS::mbedx509` and `MbedTLS::mbedcrypto` (the upstream CMake package of 3.x does, from memory). When it does not, `AUTO` falls back to fetching, and `SYSTEM` is an error that names the missing targets.

## 7. The tests

All against a local TLS server of the test (Python `ssl`), with a throwaway CA and a server certificate made at the time of the test (the `openssl` command; the test is skipped where it is not there, and the CI job that builds with TLS fails on that skip). No test uses the internet.

1. A request over TLS to the server: the C driver and the Python twin print the same status, headers and body (the scenario is run in both and compared, as the others are).
2. The host name does not match the certificate: `TLS-certificate-error` in both.
3. The server certificate is signed by a CA that is not given: `TLS-certificate-error` in both.
4. No trust anchor given: `TLS-certificate-error` with the text of 5.3 in C; Python is shown to use its system store (the one deliberate difference).
5. A server that speaks plain HTTP on the TLS port, and a server that offers only TLS 1.1 or lower: `TLS-protocol-error` in both.
6. A body of more than one TLS record (over 16 KiB), and a body that ends with the closing of the connection.
7. The authority is an IP address, `127.0.0.1`, and the certificate has the IP address in its names.
8. The three timeouts during and after the handshake.
9. A build **without** the macro: `https` is the `internal-error` of today (`test_http_the_c_has_no_tls` stays).

## 8. The CI and the other checks

* A job on Ubuntu with `FUSEDWASI_TLS=ON` and the fetched Mbed TLS (the build of Mbed TLS is cached). It runs the tests of 7 and fails on a skip.
* The sanitizers and the 32-bit job (`c-checks.yml`) build the TLS header too, so they need a 32-bit Mbed TLS build; if that is too costly, the 32-bit job leaves TLS out and says so.
* The MSVC job compiles the header at `/W4 /WX` **[not checked: that the headers of Mbed TLS are clean at that level; if not, they are included as system headers]**. macOS and Windows are added after Ubuntu is green, one at a time.
* `public_api.json` lists the three new fields of the state and the macro; `public_api.md` is made from it again; `host_scope.md` and `release_checklist.md` move the limit "`https` in C" from deferred to fixed (for the build with TLS).

## 9. What the owner has to decide

1. **Mbed TLS 3.6 (LTS)**, pinned by URL and SHA-256, fetched with `FetchContent_MakeAvailable` or found with `find_package`. (Proposed.)
2. **The trust anchors come from the embedder** (a file or a PEM in memory), with no system store in this version. (Proposed.)
3. **The Python twin gets the same setting**, and keeps its system store when none is given: the one deliberate difference. (Proposed.)
4. **`TLS-alert-received` is not used** in either twin in this version. (Proposed.)
5. **The installed package does not export Mbed TLS.** The component `tls` finds it or fetches it in the project of the embedder (`FUSEDWASI_TLS_MBEDTLS_SOURCE=AUTO|SYSTEM|FETCH`, default `AUTO`). (Proposed; the other way is to install a static Mbed TLS with the library, which makes the package heavy. It can be added later as an option without breaking this.)

## 10. Risks that are not decided

* The size and the build time of Mbed TLS in the CI, and the 32-bit and MSVC builds of it.
* `psa_crypto_init()` and the entropy source: MicroPython calls the first; whether 3.6 needs it for a TLS 1.2 client has to be read at the time of the work **[not checked]**.
* The wall clock for the validity of a certificate comes from the system (Mbed TLS), not from the `clock` of the state of the host. A guest that is given a fake clock still sees the real time in the check of the certificate. This should be written down; it is not changed here.
* Mbed TLS 4.0 splits the crypto into a separate project (TF-PSA-Crypto) and changes its API; a move from 3.6 is a later spec.
* A security fix of Mbed TLS means a new pin and a new release of the library. The pin is the place where that is done, and the spec makes it one line.

## 11. The steps, one commit each

1. The header-only layer `fusedwasi_p2__http_conn`; the plain path moved onto it with no change of behaviour (the existing http tests, in C and in Python, stay green).
2. The state fields, the Python setting of the trust anchors, and the mapping of the errors in Python (no TLS in C yet; the tests that are about Python only).
3. The header `wasi_p2_http_tls_mbedtls.h` and the macro; the C tests 1 to 8 against the local server, with the CMake module `FusedwasiTls.cmake`, the component `tls` in `fusedwasi-config.cmake.in` (and `check_required_components`), and the fetched Mbed TLS. A test in `tests/test_package.py` style: a small project that does `find_package(fusedwasi COMPONENTS tls)` against the installed package, once with `AUTO` and once with `SYSTEM` where Mbed TLS is installed.
4. The CI job on Ubuntu; then the sanitizers, 32 bits, MSVC, macOS, Windows, one after the other.
5. The documents: `host_scope.md`, `release_checklist.md`, `public_api.json` and the document made from it, `README.md` (the feature list says "TLS in Python only").
