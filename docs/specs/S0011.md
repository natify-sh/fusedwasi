# S0011: The Python twin on Pyodide (state of 2026-11-05, deferred)

**Status:** draft, **deferred**. Split out of [S0009](S0009.md) on 2026-11-05 (S0009 kept PyPy and the refused hard link; this one has Pyodide). The owner (2026-11-05) put it aside: for now only what is known is written down (section 6). The rule that was given: if the run on Pyodide is all right, Pyodide becomes a supported Python. **It is not all right** (section 1.2: 15 failures and 8 errors, every one a thing that Emscripten lacks), so Pyodide stays **not supported**. Nothing of it is decided, fixed or run in the CI. The facts are marked as in the other documents of `docs/`.

## 1. What was run

Both locally, on Linux x86-64, from the tests of the repository, on 2026-11-05. **Not run in the CI.**

### 1.1 Pyodide (the npm package, Node 22), the files of `tools/android_check.py` **[run]**

The package `fusedwasi` imports, 74 tests pass, 15 fail and 8 error. The causes seen in the output, all of the Emscripten system and not of the library:

* no `os.link` (2) and no `os.mkfifo` (9);
* no threads, `RuntimeError: can't start new thread` (8: the tests with a server in a thread);
* no real sockets: `socket.SO_REUSEADDR` is missing (2);
* the times of files have a resolution of a second (`st_mtime_ns` ends in `000`), and `set-times-at` fails (2);
* one failure, `assert 1 == 0`, **not looked into**.

`pytest` was put on the path as pure Python, because the loader of Pyodide in Node could not fetch packages from the CDN through the proxy of the session **[run]**. A WASI host that is itself in a WebAssembly runtime in a browser needs a WebAssembly engine under it; whether that is a use that anybody has **[not checked]**.

### 1.2 Pyodide again, 2026-11-05, with the recipe of `natify-sh/py-wasmhost` **[run]**

Pyodide 314.0.7 (CPython 3.14.2, `emscripten`) from the npm package on Node 22.23.4; the repository mounted with `mountNodeFS`; `pytest` and its pure-Python dependencies installed from PyPI on the host and put on `sys.path` (the CDN of Pyodide is closed to this session). The files of `tools/android_check.py`: **81 passed, 15 failed, 8 errors, 50 skipped** (the 50 skips are the C twin and the ctypes route of Windows, as on Android). The failures are all of the Emscripten system, not a result that the library gives wrongly:

* `os.link` and `os.mkfifo` do not exist (`AttributeError`): 9 failures in the scripts of `p1` and `test_memory_remote.py`, and `test_values`;
* threads cannot start (`RuntimeError: can't start new thread`): the 8 errors, all in `test_wasi_p2_http.py` (a server in a thread);
* `socket.SO_REUSEADDR` does not exist: 2 failures in `test_wasi_p2_sockets.py`;
* the times of files have a resolution of one second (`utime` of `...000000500` ns reads back `...000000000`), and `utime` with `follow_symlinks=False` is not supported (`os.supports_follow_symlinks` is only `chown` and `stat`): 2 failures of `set-times-at`;
* **new:** `os.symlink` exists but is not in `os.supports_dir_fd` (the list there is `chmod chown lstat mkdir open readlink rename rmdir stat unlink utime`), so `os.symlink(target, name, dir_fd=fd)` raises `NotImplementedError("dir_fd unavailable on this platform")` out of `symlink_at`. This is the same shape as the missing `os.link` that `link_at` now answers as `unsupported`; `symlink_at` has no such guard yet **[read: `_symlink` in `wasi_p2_filesystem.py`]**.

So **not everything is fine**: the condition "all is well, then it is supported" is not met by the run as it stands. What it would take is in section 2, option B, and in section 6.

## 2. Options

* **A. Nothing (today).** Pyodide is written as not supported (`host_scope.md`, `release_checklist.md`). The cost is zero.
* **B. Pyodide as a supported Python.** Needs a decision first on what a hard link, a FIFO, a thread, a socket option and a finer time of a file are there (the tests that need them skip with a reason, and the library answers with the error of the system), `symlink_at` guarded as `link_at` is, then a job under Node. A larger piece of work, and its use is **[not checked]**. The steps are in section 6.
* **C. Only the hard link.** Done in [S0009](S0009.md) (option D there): every refusal of a hard link has a pinned code, and a Python with no `os.link` answers `unsupported`.

## 3. Decision (owner, 2026-11-05)

Deferred: option A for now, with this document as the record. Nothing else is to be done until a user with a use for Pyodide is known, or the owner says otherwise.

## 6. What is known (written 2026-11-05)

**How to run it.** Pyodide 314.0.7 (CPython 3.14.2, `sys.platform == "emscripten"`), the npm package, on Node 22 here and Node 24 in the CI of `py-wasmhost` **[run; read]**. The recipe is in `natify-sh/py-wasmhost` **[read: `.github/workflows/tests.yml`, job `pyodide`; `tests/pyodide_run.mjs`]**: `actions/setup-node` (node 24), `npm install --no-save --prefix "$RUNNER_TEMP/pyodide" pyodide@314.0.7`, then a small Node script that does `loadPyodide({packageCacheDir, packageBaseUrl: https://cdn.jsdelivr.net/pyodide/v<version>/full/})`, `py.mountNodeFS("/repo", <the checkout>)`, `py.loadPackage(["pytest", "packaging"])` (and `h11`, the dependency of the Python twin, pure Python), and `pytest.main([...])` inside Pyodide. In this session the CDN `cdn.jsdelivr.net` is refused by the proxy, so `pytest` and its pure-Python dependencies (`iniconfig`, `packaging`, `pluggy`, `pygments`) were installed with `pip --target` on the host and mounted with `mountNodeFS("/site", ...)`; `sys.path` got `/site` and `/repo/src`; the files of `tools/android_check.py` were run with `pytest.main`. `py-wasmhost` is the one example; `waboros/docs/PYODIDE.md` is a different experiment (a guest wasm as an Emscripten side module through `ctypes.CDLL`) and not a CI recipe. Neither `fusedwasi` nor the other natify-sh repositories (waboros, py-wasmext, mpwasm) has a Pyodide CI job; the code search of GitHub found nothing, the files were read from clones **[read]**.

**What Emscripten lacks (all [run], section 1.2):**

| Missing or different | Where it shows |
| --- | --- |
| `os.link`, `os.mkfifo` do not exist | `p1` scripts (FIFO, links), `test_values`, `test_memory_remote.py`; `link_at` now answers `unsupported` |
| `os.symlink(..., dir_fd=)` is `NotImplementedError` (`os.supports_dir_fd` there: `chmod chown lstat mkdir open readlink rename rmdir stat unlink utime`) | `symlink_at` raises out of the call: **not guarded yet** (`link_at` is) |
| `utime(follow_symlinks=False)` is not supported (`os.supports_follow_symlinks`: `chown`, `stat`); times of files have a resolution of one second | the two tests of `set-times-at` |
| threads cannot start (`can't start new thread`) | the 8 errors of `test_wasi_p2_http.py` (a server in a thread) |
| `socket.SO_REUSEADDR` does not exist | 2 tests of `test_wasi_p2_sockets.py`; the sockets of `wasi:sockets` use it (`wasi_p2_sockets.py`, line 410 at this commit) |

**What would make it supported (not done):** (1) guard `symlink_at` as `link_at` is, and look at the other calls that pass `dir_fd` (`rename`, `utime`, `readlink` are on the list that Emscripten supports; `symlink` and `link` are not); (2) in the tests that need a hard link, a FIFO, a thread, `SO_REUSEADDR` or finer times, skip with a reason that names Emscripten, and allow those reasons in `FUSEDWASI_ALLOWED_SKIPS` as `tools/android_check.py` does; (3) a job (informative, not required for a merge, as `android` is) with the recipe above; (4) say in `README.md`, `host_scope.md`, `release_checklist.md` that Pyodide is supported, with this list of what it does not have. Open: what the times of a second should be (a normal answer of the system, or a refusal); whether a browser, and not Node, is a target **[not checked]**; whether anybody has a use for the host in Pyodide **[not checked]**.
