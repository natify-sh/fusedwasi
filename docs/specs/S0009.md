# S0009: The Python twin on PyPy and on Pyodide (state of 2026-11-05, nothing fixed)

**Status:** draft (a record of what was seen, and a proposal; nothing is decided and nothing is fixed). The owner said (2026-11-05) that fixing this is **not now**: the state is written here so that it is not lost. The facts are marked as in the other documents of `docs/`.

## 1. What was run

Both locally, on Linux x86-64, from the tests of the repository, on 2026-11-05. **Not run in the CI.**

### 1.1 PyPy 7.3.23 (Python 3.11.15), the whole of `tests/` without `tests/neutral/` **[run]**

310 passed, 4 failed, 17 skipped (the skips: the opt-in tests of TLS, IPv6 loopback, the `ctypes` route of Windows). The four failures have **one cause**: `os.link(src, dst, src_dir_fd=fd, dst_dir_fd=fd, follow_symlinks=False)` raises `OSError(22, 'Invalid argument')` on PyPy and works on CPython **[run: a probe, same call, same directory]**; `follow_symlinks=True` and no argument work on PyPy. The library makes exactly that call (`_link` in `src/fusedwasi/p2/wasi_p2_filesystem.py`, the line with `follow_symlinks=False`) **[read]**. The failing tests: `test_wasi_p1_core.py::test_c_and_python_agree[files]`, `test_what_the_second_stage_gives`, `test_wasi_p2_filesystem.py::test_c_and_python_agree[main]`, `test_values` (the last one fails with a `StopIteration` because the scenario goes on with the file that the link was to make).

That it is a bug of PyPy and not of the use of the call is **[not checked]** (no search of its tracker, no other version tried). Everything else passes on PyPy: sockets, http, clocks, streams, the rest of the filesystem.

### 1.2 Pyodide (the npm package, Node 22), the files of `tools/android_check.py` **[run]**

The package `fusedwasi` imports, 74 tests pass, 15 fail and 8 error. The causes seen in the output, all of the Emscripten system and not of the library:

* no `os.link` (2) and no `os.mkfifo` (9);
* no threads, `RuntimeError: can't start new thread` (8: the tests with a server in a thread);
* no real sockets: `socket.SO_REUSEADDR` is missing (2);
* the times of files have a resolution of a second (`st_mtime_ns` ends in `000`), and `set-times-at` fails (2);
* one failure, `assert 1 == 0`, **not looked into**.

`pytest` was put on the path as pure Python, because the loader of Pyodide in Node could not fetch packages from the CDN through the proxy of the session **[run]**. A WASI host that is itself in a WebAssembly runtime in a browser needs a WebAssembly engine under it; whether that is a use that anybody has **[not checked]**.

## 2. Options

* **A. Nothing (today).** CPython is the Python twin that is run and supported; PyPy and Pyodide are written here as not supported (`README.md` does not name an interpreter today **[read: no "CPython" in it]**; a line may be added when this is decided). The cost is zero.
* **B. PyPy as a supported Python.** One fix for the call (the guess: `ctypes` and `linkat` when `os.link` refuses the flag on PyPy; **[not checked]**), then a job `pypy` (a matrix entry: `uv python install pypy3.11`) with the same `pytest`. The size is small. The risk: PyPy is another interpreter with its own differences, and a job that is green today may be red with the next PyPy.
* **C. Pyodide as a supported Python.** Needs a decision first on what a hard link, a FIFO, a thread and a socket are there (the tests that need them skip with a reason, and the library answers with the error of the system), then a job under Node. A larger piece of work, and its use is **[not checked]**.
* **D. Only the hard link**: make the library say the same on every system that refuses it, and keep the other two as in A.

## 3. What the other findings of the day say

The same call, `path_link`, is the one that fails on three systems: PyPy (a flag of `os.link`), the SELinux of an Android app (`avc: denied { link }`, **[run: the log of the job `android`]**) and Pyodide (no `os.link`). So `path_link` is the least portable call of the Python twin, and a test that needs a hard link now skips where the system refuses one (`test_values`, reason "this system refuses a hard link to a program"). The code that the host gives when the system refuses a hard link on Android is **[not checked]**.

## 4. Proposal (a draft)

A for now, as the owner said, with this document and the line in `docs/release_checklist.md` (section 6) as the record. When PyPy is wanted: B, in the order: the fix, the test that pins it, the job. Pyodide: only when a user with a use for it is known.

## 5. For the owner to decide (later)

1. Is PyPy to be a supported Python, with a job?
2. Is Pyodide to be supported at all, or written as not supported?
3. Is the hard link (`path_link`) to have a documented behaviour on a system that refuses it (the error of the system, as now)?
