# S0009: The Python twin on PyPy, and the hard link that some systems refuse (state of 2026-11-05)

**Status:** implemented 2026-11-05. PyPy 8 (3.12 and 3.11) runs in the CI and is green; a PyPy before 8.0 is an expected failure with a message (section 3.1); the refused hard link has a pinned code in both twins (section 3). Pyodide was part of this document and is now [S0011](S0011.md) (deferred). The facts are marked as in the other documents of `docs/`.

## 1. What was run

Locally, on Linux x86-64, from the tests of the repository, on 2026-11-05; the CI since the same day (section 3.1).

### 1.0 PyPy 8.0.1 (Python 3.12.15), the same run, 2026-11-05 **[run]**

322 passed, 17 skipped, 0 failed: the same numbers as CPython 3.13 on the same machine. The call of 1.1, `os.link(..., follow_symlinks=False)` with `src_dir_fd` and `dst_dir_fd`, works there. So the refusal of 1.1 is gone from the current PyPy (the claim that it was a bug of PyPy is now more likely; its tracker was still not read). PyPy 8.0.1 is not known to `uv` 0.11.32 (the newest it lists is 3.11.15); `uv` 0.13.7 lists 3.12.15 and 3.11.17. ### 1.1 PyPy 7.3.23 (Python 3.11.15), the whole of `tests/` without `tests/neutral/` **[run]**

310 passed, 4 failed, 17 skipped (the skips: the opt-in tests of TLS, IPv6 loopback, the `ctypes` route of Windows). The four failures have **one cause**: `os.link(src, dst, src_dir_fd=fd, dst_dir_fd=fd, follow_symlinks=False)` raises `OSError(22, 'Invalid argument')` on PyPy and works on CPython **[run: a probe, same call, same directory]**; `follow_symlinks=True` and no argument work on PyPy. The library makes exactly that call (`_link` in `src/fusedwasi/p2/wasi_p2_filesystem.py`, the line with `follow_symlinks=False`) **[read]**. The failing tests: `test_wasi_p1_core.py::test_c_and_python_agree[files]`, `test_what_the_second_stage_gives`, `test_wasi_p2_filesystem.py::test_c_and_python_agree[main]`, `test_values` (the last one fails with a `StopIteration` because the scenario goes on with the file that the link was to make).

That it is a bug of PyPy and not of the use of the call is **[not checked]** (no search of its tracker, no other version tried). Everything else passes on PyPy: sockets, http, clocks, streams, the rest of the filesystem.

## 2. Options

* **A. Nothing (today).** CPython is the Python twin that is run and supported; PyPy is written as not supported. The cost is zero.
* **B. PyPy as a supported Python.** ~~One fix for the call~~ **No fix is needed for PyPy 8.0.1 (section 1.0: the whole run passes); only PyPy 7.3.x refuses the flag.** What is left is a job `pypy` (a matrix entry; a `uv` that lists 3.11.17 or 3.12.15, or the archive of PyPy) with the same `pytest`, and the decision of whether 7.3.x is supported (a retry without the flag on `EINVAL` would be the fix, **[not checked]**). The size is small. The risk: PyPy is another interpreter with its own differences, and a job that is green today may be red with the next PyPy.
* **C. Pyodide as a supported Python.** Moved to [S0011](S0011.md).
* **D. Only the hard link**: make the library say the same on every system that refuses it.

## 3. What the other findings of the day say

The same call, `path_link`, is the one that fails on three systems: PyPy (a flag of `os.link`, before 8.0), the SELinux of an Android app (`avc: denied { link }`, **[run: the log of the job `android`]**) and Pyodide (no `os.link`, [S0011](S0011.md)). So `path_link` is the least portable call of the Python twin, and a test that needs a hard link skips where the system refuses one (`test_values`, reason "this system refuses a hard link to a program").

**Option D is done (2026-11-05):** the error code of each refusal is pinned by `test_a_refused_hard_link_gives_the_error_of_the_system` (`EACCES` is `access`, `EPERM` `not-permitted`, `EINVAL` `invalid`, `ENOTSUP` `unsupported`, `EXDEV` `cross-device`), and a Python with no `os.link` (`AttributeError`, `NotImplementedError`) answers `unsupported` where it used to raise out of the call (`link_at` in `wasi_p2_filesystem.py`). The C twin needs no change: it gives the same codes through the table of errno that is compared with the Python one, and it is pinned for these refusals by `test_a_refused_hard_link_gives_the_same_code_in_c` (POSIX; Windows is not covered, it maps `GetLastError`). Documented in `host_scope.md` and `features.json`. Not seen: the code of a real refusal on Android (the tests simulate it).

## 3.1 Decision on PyPy before 8.0 (owner, 2026-11-05)

A failure on PyPy 3.11 was allowed, with a message that names the bug and advises PyPy 3.12. **Corrected the same day:** the version that matters is PyPy 8.0, not Python 3.12; PyPy 3.11.17 is PyPy 8.0.1 and passes (CI, below). So the failure is allowed on **PyPy before 8.0 (7.3.x)**, and the message advises PyPy 8.0 or newer. Done in `tests/conftest.py`: on a PyPy that refuses `os.link(..., follow_symlinks=False)` (a probe, not a version number), the four tests that make a hard link by that call are `xfail` (not strict) with the message, and the header of the run carries it as a WARNING. On CPython and on PyPy 8 nothing changes. **[run]** PyPy 3.11.15 (7.3.23): 318 passed, 17 skipped, 4 xfailed; PyPy 3.12.15 (8.0.1): 322 passed, 17 skipped; CPython 3.13: 322 passed, 17 skipped. The library is not changed (a retry without the flag on `EINVAL` stays an idea, not done). **In the CI since 2026-11-05** (job `pypy` of `test.yml`, run 42022072741): PyPy 3.12.15 (8.0.1) and PyPy 3.11.17 (8.0.1) both green; the 3.11 job printed `335 passed, 33 skipped` with no xfail, so the xfail path is not run in the CI (no PyPy 7.3.x there), only by hand. In the same run the jobs on Windows, macOS, Ubuntu and Android were green with the tests of the refused hard link.
