# S0003: Streaming of `wasi:http` bodies (the answer is read whole today)

**Status:** accepted 2026-11-05 and **implemented in the Python twin the same day** (option B: the body of the answer is a stream, on `h11`; see [S0013](S0013.md), step 3). The C twin still reads the answer whole (an `xfail(strict=True)` pins it). The streaming of the request body (option C) is open (S0013, section 8, item 1). The facts are marked as in the other documents of `docs/`.

## 1. The problem

The host reads the whole answer before the guest sees it; a body is a stream over bytes in memory, at most `MAX_BODY` (256 MiB), and the end is `closed` **[read: `wasi_p2_http.py` header comment, `MAX_BODY = 1 << 28`; `FUSEDWASI_P2_HTTP_MAX_BODY` in `wasi_p2_http.h`]**. Three consequences, each a thing a guest can see:

1. a body larger than the limit fails the request (`HTTP-response-body-size`) **[read]**;
2. a guest that wants the first bytes of a slow or endless body (a log, server-sent events) waits for all of it, or for the limit;
3. a body that breaks halfway fails the whole request, where Wasmtime gives the first part **[read: `host_scope.md`, Known limits; Wasmtime's behaviour **[not checked]** here: stated by `host_scope.md`]**.

## 2. Options

* **A. Keep it, document it (today).** Cost: nothing. Consequence: the three things above stay. The alpha is unstable by its own words, so this is allowed to stay for the alpha.
* **B. Streaming in the answer only.** The connection layer (`fusedwasi_p2__http_conn`: read/write/close) already reads in pieces; the body stream would read from the connection when the guest reads, and `subscribe` would be the readiness of the descriptor. The request body stays whole (a guest writes into memory and `finish` sends). Both twins, one design.
* **C. Streaming both ways** (a request body sent while the guest writes). Needs the headers to be sent before the body is complete (chunked encoding), so a connection that stays open while the guest runs.

## 3. What decides it

* The hook of S0001 owns its own waiting; for B the hook's `read` already has a timeout, so a body read in pieces fits the hook **[read: `docs/tls_hook.md`, section 2]**.
* A host that is called from a single thread must not block in `read` of a body: the stream has to be non-blocking and `subscribe` has to say when it is ready. This is the larger part of the work **[not checked: an estimate, no code written]**.
* The twin parity: the Python twin would use a socket in the same way (non-blocking, `select`); the tests of the twins (C against Python) must see the same pieces for the same server.

## 4. Proposal (a draft, nothing decided)

Option B, in two steps: (1) the answer body is a stream over the connection with a pollable `subscribe`, the limit kept as a limit of the total; (2) an answer that breaks halfway gives the guest the part it had and then the error through `http-error-code` of the future, as the WIT describes.

## 5. For the owner to decide

1. Is streaming of the answer wanted before the alpha ends, or after a real program asks for it?
2. If it is wanted: B only, or B and C?
3. Is the limit of 256 MiB kept as the total, or removed when the body streams?
