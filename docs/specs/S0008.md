# S0008: The comparison with Wasmtime in the CI

**Status:** draft (a proposal; nothing is decided). Written 2026-11-05 so that an open question of `docs/release_checklist.md` (section 6) is not lost. The facts are marked as in the other documents of `docs/`.

## 1. The problem

The comparison of fusedwasi with Wasmtime (`docs/wasmtime_compare.md`, `docs/experiments/wasmtime_compare/`, `tools/wasi_p2_conformance/`) is run by hand. A change can make an agreement into a difference without anyone seeing it until the next manual run. Also not compared with a real host: sockets, terminals, a real stdin; and Windows, macOS, ARM64 and 32-bit run the C drivers against the Python twin only **[read: release_checklist, section 6]**.

## 2. What it needs, from PyPI **[read, 2026-11-05]**

`wasmtime` 50.0.1 (wheels for Linux x86_64 and aarch64, macOS x86_64 and arm64, Windows x64 and ARM64) and `wasm-tools-package` 1.263.0.0 (the prebuilt `wasm-tools` of the Bytecode Alliance, source `natify-sh/wasm-tools-package`; **not** the PyPI project `wasm-tools`, which is a pure-Python parser). Also needed: the WIT of 0.2.12 (the repository carries it in `tools/spec_sources/wasi_p2/`, which may serve **[not checked]**) and, only for the filesystem and http experiments, the Rust guest (`wasm32-wasip2`). **[not checked]:** that the harness runs with these packages; nobody has run it so.

## 3. Options

* **A. A job that runs the harness and fails on a difference that is not listed** (the list of deliberate rows is data, in the compare document or a file next to it). The strongest, and the most work: the rows have to be machine-readable.
* **B. A job that runs it and only reports** (the output in the log or an artifact). Cheap; nobody reads it.
* **C. A scheduled run** (weekly), not on every push: the Rust guest and the build are slow.

## 4. Proposal (a draft)

First step: make the harness run in one job on Ubuntu with the two PyPI packages (answers the [not checked] above) in report mode (B). Second step: a list of known differences as data and a failure on a new one (A), with the schedule of C if the run is too slow for every push.

## 5. For the owner to decide

1. Is a job in the CI wanted at all, on every push or on a schedule?
2. Is the Rust guest allowed in the CI (a toolchain install in the job)?
3. Is the report mode enough as the first step?
