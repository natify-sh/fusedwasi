# The size of a host of WASI 0.2

Status: **a count, 2026-10-22; the tables below are of that day, and since then all 200 imports have a function in Python and in C (`audit_sigs.py`: 0 differences), the 5 stubs of the filesystem do the work, and sockets, filesystem and http run on Windows.** See the lines of the packages at the end for what each does and does not do. How a fact is known: **[read]** the WIT of the tag `v0.2.12` of `WebAssembly/WASI` (the repository also has the branch `wasi-0.2`), parsed with `wasm-tools component wit --json`;
**[run]** the imports of the programs of the studies ([wasi_p1_vs_p2_host_requirements.md](wasi_p1_vs_p2_host_requirements.md)) and the hosts in `examples/`. Script and full table:
[experiments/wasi_p2_scope/](experiments/wasi_p2_scope/).

## The size, in numbers

WASI 0.2 is **7 packages** (`cli`, `clocks`, `filesystem`, `http`, `io`, `random`, `sockets`), **31 interfaces**. For a host the unit is an **import**: a function, or the `[resource-drop]` of a resource.
Without the two exports (`wasi:cli/run#run`, `wasi:http/incoming-handler#handle`) and without the unstable items (4 functions, hidden behind features):

| Package | Interfaces | Functions | Drops | **Imports** | Seen in programs | Implemented | Stubbed |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| cli | 11 | 11 | 2 | 13 | 12 | 10 | 0 |
| clocks | 2 | 6 | 0 | 6 | 6 | 6 | 0 |
| filesystem | 2 | 30 | 2 | 32 | 29 | 24 | 5 |
| http | 3 | 52 | 11 | 63 | 0 | 0 | 0 |
| io | 3 | 19 | 4 | 23 | 12 | 11 | 0 |
| random | 3 | 5 | 0 | 5 | 1 | 1 | 0 |
| sockets | 7 | 52 | 6 | 58 | 55 | 17 | 0 |
| **all** | **31** | **175** | **25** | **200** | 115 | 69 | 5 |

- **A command (the world `wasi:cli/command`) can import 137 of them in 27 interfaces** (everything above except `http`). The world `wasi:http/proxy` imports 97 in 11 interfaces (it shares io, clocks, random and a part of cli
  with the command world, and adds the 63 of `http`).
- **Four programs asked for 115 of the 137** (git, git with sockets, hello, CPython with OpenSSL; all C on wasi-libc). **22 were never asked for** by any of them: `initial-cwd`, `descriptor.get-type`, `is-same-object`,
  `filesystem-error-code`, `error.to-debug-string`, `pollable.ready`, the blocking/`skip`/`splice`/`flush`/`write-zeroes` stream calls, `get-random-u64`, `insecure*`, the unused `network` drop and similar.
- The biggest groups: **`http/types` 62** (51 functions and 11 resources: fields, requests, responses, bodies, futures), **`sockets/tcp` 29**, **`filesystem/types` 31**, **`sockets/udp` 21**, `io/streams` 17.

## What the hosts here implement

| Host | Lines | Answers |
| --- | ---: | --- |
| `examples/wasi2_unbundled` `Host` | 293 | stdout/stderr, clocks, `poll`, a TCP client (connect, read, write); the rest raises `NotImplementedError` |
| `examples/wasi2_python` `FsHost` + `NetHost` | 442 + 121 | arguments, environment, `exit`, `random`, clock resolutions, **24 of the 30 filesystem functions**, name lookup (IPv4), TCP client with address/shutdown |

Counted by name: **69 of the 200 imports are implemented, 5 are stubs** (`advise`, `sync`, `sync-data`, `set-times`, `set-times-at` answer ok and do nothing). Of the 137 of the command world, **40 were asked for and are
not implemented**: **35 in `wasi:sockets`** (18 of `tcp`, all 18 of `udp`, `create-udp-socket`: bind, listen, accept, options, datagrams) and the 5 stubs. So **what a CPython or a git on WASI 0.2 asks for is
covered by the host of `wasi2_python` except UDP and the server side of TCP**; that is why `print`, `ssl`, an HTTPS request and `pip install` ran.

## Size of the rest **[estimate]**

- To cover the **command world** (137): +63 imports on top of the 74 answered. About **35 of them are sockets** (`bind`, `listen`, `accept`, the socket options, UDP) and are the same kind of code as the TCP client
  already written (a handle table and the `socket` module of Python): in the order of 200 lines. The rest (`blocking-*` streams, `skip`, `flush`, `get-random-u64`, `initial-cwd`, `get-type`, `is-same-object`, `to-debug-string`, `pollable.ready`,
  the real `set-times`/`sync`) are one to ten lines each.
- **IPv6** is not written in the sockets (the address variants are flattened to more numbers); it adds code to every call that takes an address.
- **`wasi:http` (63) is another size**: the host needs an HTTP client and, for `incoming-handler`, a server, and the types (`fields`, `request`, `response`, `incoming-body`, `future-incoming-response` with `poll`) are
  resources with ownership rules; no program here uses it. It is the largest block after sockets and filesystem, and CLI programs do not need it.
- **Not a sandbox:** the filesystem host trusts the guest's paths (`..`, symbolic links); a real host has to confine them. This is a size, not a count.
- The implemented functions are not all complete: for example `input-stream.read` never blocks (it answers an empty list when nothing is ready) and the TCP connect is blocking.

## Against the WASI 0.1 the first user has in C

the first user's WASI 0.1 (`wasi_core.h`, 1990 lines in C inside the module) answers `wasi_snapshot_preview1` in C (the study counted 42 of the 46 calls the programs made) and asks the host for none; WASI 0.2 asks the host for **137 imports for a command** (200 with `http`).
Same programs, same results ([wasi_p1_vs_p2_host_requirements.md](wasi_p1_vs_p2_host_requirements.md)). A host of 0.2 inside the module would be a work of the size of `wasi_core.h` plus the canonical ABI
(strings, lists, results through memory, resources as handles).

## The layout of a host of WASI 0.2 in C (a plan, 2026-10-22; nothing of it is built)

Decided in the discussion (the owner's constraint stays: a host of 0.2 is an example, not a part of the first user, until it is decided otherwise):

- **Like `wasi_core.h` of 0.1, one file per package, header-only, every function `static`**, so that the compiler drops what a module does not use. `wasi_core.h` is 1990 lines for the 46 calls of 0.1 on three systems; 137 imports of the command world are estimated at **4 to 6 thousand lines** of C (an estimate from the sizes of the Python hosts in `examples/`, 293 + 442 + 121 lines for 69 imports; not measured).
- **No `#define` for the choice of a function or a package.** The defines stay what they are in 0.1: the system and the backend of files (`_WIN32`, `WASMEXT_WASI_PYTHON_FS`). **The choice is made by the generator, from the names of the imports of the module** (`wasi:cli/stdout@0.2.12` and so on), as for 0.1 it is made from `wasi_snapshot_preview1` / `wasi_unstable`; it includes the files of the packages that appear and the ones they need. A version `@0.2.x` is matched by its prefix, so that a host works with `0.2.6` and with `0.2.12`.
- **The files** (prefix `wasi_p2_`, so that no name meets `wasi_core.h`; each includes what it needs and has a guard):

| File | What | Includes |
| --- | --- | --- |
| `wasi_p2_core.h` | the state of the host, the **one table of resources** (streams are used by cli, filesystem and sockets), the helpers of the canonical ABI (strings, lists, records, variants, option, result, flags, resources) | |
| `wasi_p2_io.h` | streams, poll, error | core |
| `wasi_p2_clocks.h`, `wasi_p2_random.h` | clocks, random | core |
| `wasi_p2_cli.h` | stdin, stdout, stderr, environment, exit, terminals | io |
| `wasi_p2_filesystem.h` | filesystem | io, clocks |
| `wasi_p2_sockets.h` | sockets (Winsock on Windows: `-lws2_32`), the part that is not implemented answers "not implemented: name" | io, clocks |

- **`http` is not in the first round** (63 imports of the world `wasi:http/proxy`, not of `command`; none of the four programs asked for one): a file `wasi_p2_http.h`, included only when the module imports `wasi:http/...`, if a component of Rust or JavaScript has to be run.
- **Names** carry the interface (`wasi_cli_stdout_get_stdout`): `get-stdout` and similar names repeat in the interfaces, which in 0.1 they did not.
- **What the module asks for is the check:** an import that the host has no function for becomes a function that traps with "not implemented: <name>", and the build says it; the list of the requirements of a module (21 imports for the simple pair, 42 for the complex one) is the test.
- **Several memories** (a module fused by meld has one for each component): the call of an import takes the memory and the `cabi_realloc` of its component, which the import map of meld 0.65 states (`"version": 2`); the host of 0.1 is bound to one memory.
- **The types of WIT** are not in the fused core module (it has flat `i32`); they come from `wasm-tools component wit --json` of the source component. A generator of the glue from the official WIT (a script in the repository, its result committed) was suggested for the repetitive lifting and lowering, **once, not for each module**; the bodies (what `path_open` does) are written by hand and some of them can use the backend of 0.1.

### Is anything in the plans a blocker for `wasi_p2_*.h`? (a check, 2026-10-22)

Read in FEATURES.md ("What is open"), `where_we_stopped`, `abi_policy.md` and the notes: **no.** WASI 0.2 has no row among the open items that it depends on, and the pieces it needs are there: multi-memory (done), a core module fused by meld 0.65 (the bugs #512/#513 fixed), the repair of imported functions in element segments (`_repair_imported_elements`, and WABT #2903), `wasi_flavor` (tells a component from a fused module), the state of a host per instance as in `WASI_STATE` of 0.1 (so the context is **not** needed). What is new work: the generator part that binds the imports `(interface, name)` to the functions, the choice of memory and `cabi_realloc` for each import (the host of 0.1 is bound to one memory), the canonical ABI helpers and the bodies. The files would be in `src/<first user>/c/`, which are in the fingerprint of the ABI (`tests/test_abi.py`): a new file only adds, so the fingerprint changes and the number stays (`abi_policy.md`). **The one constraint is the owner's earlier decision that a host of 0.2 is an example and not a part of the first user; it is the owner's to lift.**

### The shape of the host: parallel C and Python, flat functions, a state and no globals (decided in the discussion, 2026-10-22)

- **Two hosts in parallel with the same structure:** `wasi_p2_*.h` (C) and `wasi_p2_*.py` (Python), a file for a package in each. They are tested **apart from the AOT compiler** (`natify`/wasm2c is not needed): a test gives a host a fake memory (an array of bytes) and the arguments as the flat ABI of the core module gives them, and reads the results out of the memory; the C and the Python host get the same input and their outputs are compared; the behaviour is compared with Wasmtime on the same components. A module through wasm2c is the integration test later. The Python host may later move to a repository of its own (it has to depend on nothing of the first user: a memory and values in, values out; what is in that repository was not looked at).
- **One table of the signatures, made once from the WIT** (`wasm-tools component wit --json`), used by both, so that they do not drift. A subset first (clocks, random, cli, io/streams, the minimum of the filesystem), parity proved, then the rest: not 137 functions twice at once.
- **The surface is flat functions**: in the fused core module a method is `[method]output-stream.write(handle, ptr, len, retptr)`, a constructor `[constructor]...`, a resource is an `i32`. **The state is not flat**: a table of handles (`own`/`borrow`, drop), streams of several kinds behind one interface (stdout, a file, a socket, a pipe: classes in Python, a struct with a tag and function pointers in C) and pollables. Not a deep hierarchy: the table and one or two base types.
- **No globals.** Everything that changes (the table, streams, pollables, the bound memories and `cabi_realloc`, buffers) is in one structure `wasi_p2_state` made for an instance and passed as the first argument (`void *s`, like `WASI_STATE(s)` of 0.1); no mutable `static` and no thread-local in `wasi_p2_*.h`; in Python a class `Host` holds the table and there is no mutable state at the level of the module. Constant tables (names, signatures) are allowed. What two instances share (a common stdout) is passed in explicitly when they are made. Reasons: several instances and several modules in one process, threads and free-threading, tests in parallel, the context. Also: a handle carries a generation counter to catch a use after the drop; the state is "one thread for a state" or has a lock (to be chosen and written down); the state holds the memory of each component by number, and an import takes its own.

### Where the files are, and what is built (2026-10-22)

**Decided by the owner: the host of 0.2 becomes a part of the first user, but is not in the ABI yet.** The constraint "an example, not a part of the first user" is lifted. The files:

- C: `src/<first user>/c/p2/wasi_p2_<package>.h`; Python: `src/<first user>/p2/wasi_p2_<package>.py` (a subpackage, `<first user>.p2`). The C is in a **subdirectory**, which `abi_fingerprint` does not read (it reads the files of `c/` only), so the ABI number and the fingerprint do not change; `pyproject.toml` ships both. Nothing here is promised, and no module of the generator includes them yet.
- **Built: `core`, `clocks` (6 imports), `io` (23 imports: `error`, `poll`, `streams`), `random` (5 imports), `cli` (13 imports), `filesystem` (32 imports) and `sockets` (58 imports)** — that is **the whole of the command world** (137 imports) — **and `http` (63 imports, the other world; see the paragraph on http below)**, C and Python, one package at a time as decided. Core: `wasi_p2_state` / `Host` (memories by number, the table of handles with a generation in the top 12 bits and the index in the low 20, the clocks as hooks so that tests can fix them, a `trap` hook), the checked little-endian stores. No mutable global.
  Clocks: `wall-clock` `now`/`resolution` (a `datetime` through the pointer), `monotonic-clock` `now`/`resolution`/`subscribe-instant`/`subscribe-duration` (a pollable is a slot of the table with an object that answers `ready`, which `io` shares: deadlines, streams).
  Io: `error` (`to-debug-string` through the `cabi_realloc` of the component, a hook of the state), `poll` (`ready`, `block`, `poll` of a list, an empty list traps), `streams` (read/skip, write/check-write/flush, `write-zeroes`, `splice` and the blocking forms, `subscribe`, drops; a write of more than `check-write` traps; `closed` and `last-operation-failed` with an `error` resource). A stream of the host is an object with a few methods (C: a struct of function pointers); `MemoryInput` and `BufferOutput` are in the files, files and sockets come with their packages. The layouts of the results are written in `wasi_p2_io.py`.
  Cli: `environment` (arguments, variables, `initial-cwd`: lists and strings through `cabi_realloc`, list first), `exit` (`exit` and `exit-with-code`: Python raises `Exit(code)`; C calls the hook `exit` of the state, which by default records `exited`/`exit_code` and traps, as `proc_exit` of 0.1 does with its `end` hook), `stdin`/`stdout`/`stderr` and the terminals. **The standard streams are done as in the WASI 0.1 host:** the caller may give a stream; by default Python uses `sys.stdin.buffer`/`sys.stdout.buffer`/`sys.stderr.buffer` **of the moment** (the text layer is flushed first, so that a capture and the order against `print` hold) and C uses the descriptors 0, 1 and 2 (`poll` for readiness; made when first asked for, freed with the state). Every `get-stdout` is a new handle to the same stream; dropping it closes nothing. `get-terminal-*` is `none` unless the state says the stream is a terminal; the terminal resources have no methods.
  Filesystem: `preopens` and the whole of `types` (the 27 methods of `descriptor`, `directory-entry-stream`, `filesystem-error-code`, the drops). POSIX with `dir_fd` / the `*at` calls, Windows by paths (`wasi_p2_fs_win32.h`: the walk opens by name with the `\\?\` prefix; names with `\` or `:` are `invalid`; links are symlinks and junctions). **The paths are confined, as in `wasi_walk` of 0.1:** a path is walked by name, every directory on the way opened with `O_NOFOLLOW` from the one before; `..` cannot go above the directory the descriptor stands for; an absolute path or a link with an absolute target is `not-permitted`; links are expanded by hand (40 at most, then `loop`), the one at the end only with `symlink-follow`. This is a walk by name and not `openat2(RESOLVE_BENEATH)`, so a process that changes the tree under the walk is not stopped (as in 0.1). **Rights:** a descriptor has `read`, `write`, `mutate-directory`; a write without `write` is `bad-descriptor`; a change of a directory without `mutate-directory` is `read-only`, as the WIT says, but a directory opened below one that has the flag inherits the rights of its parent, whatever the guest asked for (as in Wasmtime; decided 2026-10-27: a handle opened with only `read` can be changed through, and `get-flags` reports the inherited `mutate-directory`), and a write asked from a read-only preopen is `read-only`; an absolute target of a link is `not-permitted` (`readlink-at`, `symlink-at`); a preopen can be read-only (`Host(preopens=[(path, name, False)])`, `struct wasi_p2_preopen`). Streams over a file (`read-via-stream`, `write-via-stream`, `append-via-stream`) use a duplicate of the descriptor, so they outlive its handle; the `error` of a failed file stream carries the `error-code`, which `filesystem-error-code` returns. Directory entries are a sorted snapshot without `.` and `..`. `advise` is accepted and does nothing; `metadata-hash` is two FNV-1a values: `upper` of device and inode (it names the object), `lower` also of size and modification time (it changes when the file does). The errno-to-`error-code` table is the same in both. Not done: `access` checks beyond what the system says, quotas; on Windows the sharing modes of files are the system's.
  Sockets (POSIX and Windows, real non-blocking sockets; Winsock on Windows: errors turned into errno, a failed connect seen in the third set of `select`, `SO_EXCLUSIVEADDRUSE` for `SO_REUSEADDR`, a UDP reset ignored): `network`, `instance-network`, `ip-name-lookup`, `tcp`, `tcp-create-socket`, `udp`, `udp-create-socket`. **Nothing is allowed by default, as in Wasmtime:** `Host(network=True)` allows everything, or `socket_addr_check(ip, port, use)` and `allow_ip_name_lookup` decide (`s->socket_addr_check`, `s->allow_ip_name_lookup` in C); a refusal is `access-denied`. TCP follows the states of the WIT (unbound, bind-in-progress, bound, listen-in-progress, listening, connect-in-progress, connected, closed): `start-*` makes the system call, `finish-*` reports, `finish-connect` is `would-block` until the connection is made, a failed connect closes the socket, what does not fit the state is `invalid-state`, what is not in progress is `not-in-progress`. Address checks: wrong family, multicast, broadcast, an IPv4-mapped IPv6 address, and for a connect the unspecified address or port 0 are `invalid-argument`. The streams of a connection are ordinary `wasi:io` streams (`SocketInput`/`SocketOutput`; C: a count of references keeps the socket alive for them); they close after `shutdown`, and a reset gives `last-operation-failed` with an `error` that `network-error-code` reads (`connection-reset`). UDP: `stream` with a remote address is not a kernel `connect` but kept in the socket (datagrams from other addresses are dropped; a datagram names no address, or exactly the stream's), `check-send` permits 16 datagrams and a `send` without it traps. A list returned (datagrams, addresses) is written through `cabi_realloc`. **Not done:** the properties of a listener (keep-alive, hop limit, buffers) are not copied to what it accepts (the system decides); `check-write` of a socket stream is a fixed 64 KiB and a write waits when the system buffer is full; the lookup of a name is done at once and blocks, and a name with anything but ASCII letters, digits, `.`, `-`, `_` is `invalid-argument` (no IDNA); IPv6 sockets are tested only with the checks of addresses (the machine may have no IPv6).
  Random: `get-random-bytes`/`u64`, the insecure pair and `insecure-seed` (a tuple of two u64 through the pointer); the bytes come from hooks of the state (`os.urandom`, `/dev/urandom`, `BCryptGenRandom` with `-lbcrypt` on Windows, which is not tested here), the insecure ones from the same source unless replaced; a request of more than 64 MiB and a source that fails are traps. Every C function is `static inline` (`WASI_P2_FN`) so that the unused ones do not warn.
  Http (`wasi_p2_http.py` / `wasi_p2_http.h`; `types` 62 and `outgoing-handler` 1; `incoming-handler` is an export): **an outgoing request is refused (`HTTP-request-denied`) unless `Host(http=True)`, `http_check(scheme, authority)` or `s->http_check` allows it**; the transport is a small HTTP/1.1 client of our own in both languages (`Connection: close`, `Content-Length` or chunked with trailers, 1xx skipped, `HEAD`/204/304 without a body, timeouts of `request-options`), so the two give the same bytes and the same `error-code`; TLS is only in Python (`ssl`), in C `https` is `internal-error` unless the embedder sets a transport (`Host(http_send=...)` / `s->http_send`), which is also how tests feed failures. The answer is read whole and a body is a stream over bytes (no streaming of big bodies; at most 256 MiB); a request is sent when the guest first asks for its answer; a stream of a body never fails, so `http-error-code` is always `none`. `error-code` (39 cases, 32 bytes aligned to 8) is written by a table of the shape of each payload (`CASES`), compared with the WIT by `docs/experiments/wasi_p2_audit/audit_http_cases.py`; names of fields are lower case, a few are `forbidden`, the fields of a request or an answer are `immutable`. The server side (a component that exports `incoming-handler`) is given by the embedder (`incoming_request_new`, `response_outparam_new`). **Not done:** `send-informational` (unstable); streaming of bodies; HTTP/2; redirects and proxies; the policy of sockets is not applied to http (its own `http_check` is). Test: `tests/test_wasi_p2_http.py` (a server on the loopback; C and Python agree on 11 scenarios, the C driver is clean under ASan/UBSan).

- **Tests: `tests/test_wasi_p2_clocks.py`, `tests/test_wasi_p2_io.py`, `tests/test_wasi_p2_random.py`, `tests/test_wasi_p2_cli.py`, `tests/test_wasi_p2_filesystem.py` and `tests/test_wasi_p2_sockets.py`** (the last one on the real loopback: a TCP listener, connect, accept, data both ways, shutdown, refused connection, a reset, UDP between three sockets, names, and a host that allows nothing; the ports are the system's, so what is compared is whether they match) (a real tree of files, 19 paths against the confinement, symbolic links, loops, read-only preopens, every call of `descriptor`; an extra test of the walk) (the last one also runs the descriptor streams over pipes and checks the Python default against a capture) (the C driver of the io test is clean under ASan/UBSan, run by hand): the same scenario in Python and in C (`tests/data/wasi_p2_clocks_driver.c`), fixed clocks, a fake memory; the outputs are equal (the bytes of the result, the handles, a use of a dropped handle, a pointer outside the memory, a missing memory trap). No wasm2c.
- **Not built:** the table of the signatures from the WIT (the functions are written by hand for now), the check against Wasmtime of the packages other than filesystem and http (those two were compared: `wasmtime_compare.md`), the generator part that binds `(interface, name)` to the functions, the other packages (next: `http`, which is another world). The question of what "nothing" is for a WASI import (an error code or a trap) is not decided.

### Checked against the WIT (2026-10-23)

The 79 stable imports of cli, clocks, filesystem, io and random were compared with the WIT of `v0.2.12` in two ways ([experiments/wasi_p2_audit/](experiments/wasi_p2_audit/)): by script (the flat parameters and results by the Canonical ABI, the layout of every result: 0 problems) and by reading the comments of the WIT against the code. The reading found five differences, all fixed in C and Python, each with a test: **(1)** after `last-operation-failed` a stream is closed and every later call is `closed` (a pollable of a closed stream is ready); **(2)** a missing `mutate-directory` is `read-only`, not `not-permitted`; **(3)** `readlink-at` of an absolute target and `symlink-at` to `/...` are `not-permitted`; **(4)** `metadata-hash` follows size and modification time; **(5)** `unlink-file-at` of a directory is `is-directory` also where the system says `EPERM`.
Left as it is on purpose, and different from the letter of the WIT: `blocking-write-and-flush` takes a list longer than 4096 bytes and writes it in pieces (the WIT says "up to 4096"); `get-random-bytes` traps above 64 MiB (the WIT has no limit); `sync` and `sync-data` are called on a descriptor that is not open for writing (the WIT says "no effect"); a pollable derived from a stream does not trap if the stream is dropped first (the WIT says "may trap"). **Not compared with a real host** (Wasmtime): everything above is the reading of the text, and the tests compare the C with the Python, not either with Wasmtime.

**Sockets (2026-10-23)** were checked the same way (script: the 58 imports, with the 79 before, 137 in all, 0 problems) and read against the comments of the WIT; one difference was found and fixed: with a stream made for a remote address the `remote-address` of a datagram must be none **or exactly that address** (it was refused when named). The properties of a listener that the WIT says an accepted socket inherits are left to the system (Linux does it for most); that is the one open difference of this package.

## Changes of 0.1 that 0.2 forced

WASI 0.1 is implemented over WASI 0.2 (`design_model.md`, section 4, stage B of step 3, 2026-10-27). The behaviour of every call was kept, checked three ways: the official wasi-testsuite of 0.1 (72 tests, through `tests/neutral`), the scripts of `tests/data/p1` (their output was kept from the code before the change and compared line by line), and 250-step random scripts of calls (path_open with random rights, flags and paths, reads, writes, seeks, renames, links, polls, ...) run on the code before, on the new Python and on the new C, with the same outputs. What did change, and why:

* **`proc_exit` is `wasi:cli/exit`.** It tells the hook `exit` of the guest (the default records `exited` and `exit_code` and traps, as `proc_exit` did). A host that replaced `exit` for 0.2 now receives `proc_exit` too and is the one that records `exited`. 0.1 has no `int *trapped`: a trap is `g->trap` (C) or the exception (Python), and the Python `Exit` is one class for both families.
* **`poll_oneoff` waits by asking.** When a subscription is for a descriptor that has to be waited for (the standard input of the process, a stream of the state that says whether it is ready, a pipe or a FIFO opened by a path), the call asks the pollable (for a pipe or the process's input, the system's `poll` with no wait) and, while nothing is ready and the clocks are not due, waits with the `wait` of the guest (1 ms by default), instead of blocking in `poll(2)`. A wait for clocks only is the hook `sleep`, as before. The standard input of a state that gave a stream with a `ready` is now waited for (it was answered at once).
* **Descriptors are made at the first call (or by `open_descriptors`).** A preopen that cannot be opened is no longer told by the constructor of the state (Python `PreopenError`) or `fusedwasi_p1_create`: it is told by `fusedwasi_p1_open_descriptors` / `fusedwasi.p1.open_descriptors`, and a function of 0.1 called first answers the errno of the failure (and tries again at the next call).
* **The files of 0.1 are the resources of the state, freed with it.** `fusedwasi_p2_free` / `State.close_all()` close them (there is no `fusedwasi_p1_destroy`). `fd_close` of a file or a directory drops its resource and no longer tells the error of `close(2)` (it answers SUCCESS).
* **The position of a file is the adapter's.** `fd_read`/`fd_write` are a `pread`/`pwrite` at it. A write to a descriptor opened for appending goes to the end of the file (the adapter does it; a `pwrite` on such a descriptor also goes to the end on POSIX, as the system did, and at its offset on Windows, as before). A file that cannot be read or written at an offset (a pipe or FIFO opened by a path, a terminal) is read and written at the position of the system, as before; `fd_seek`/`fd_tell` on it are the system's.
* **Python: the wall clock for `fd_filestat_set_times` / `path_filestat_set_times` with "now" is `State.clock(0)`** (the hook of the state), not `time.time_ns()`; this is what the C always did. A clock that cannot be read is a trap there (C: `g->trap`; Python: the exception of the hook), where Python used to answer an error code.
* **Python: `State.filesystem`.** The files of both families are the operations of an object (`SystemFilesystem` by default; `Filesystem()` is a host without files; a host may give its own). The Python-only `files=` backend (an interface on `Entry`) is replaced by it; see `interface_review.md`. Python errors of the system are mapped through the error-code of 0.2 (and, on Windows, the Win32 error) as the C does; an errno that 0.2 has no code for answers IO, as in the C.
* **Not changed on purpose:** the errors of the calls, the order of the checks (rights, then the directory, then the path), `.` and `..` in listings, the cookies, the layouts of `filestat` and of events in both snapshots, the rights of the standard streams and the preopens, NOTSOCK/BADF of the four socket calls.

## Known limits

**Unstable in the alpha: `wasi:sockets` (58 imports, with IPv6) and `wasi:http` (63 imports, with `https` in C).** There is no promise on their behaviour or on their names (the names of the transport and of the server side of http are listed in `public_api.md` as unstable) until a real program uses them. They are tested as the limits below say: the C against the Python twin, the address checks, a server on the loopback; not against a real host except `wasi:http` (23 requests) in `wasmtime_compare.md`. IPv6, the properties of accepted sockets, `https` in C and the bodies of http are the first four limits below.

Written 2026-10-26 from `release_checklist.md` section 3. The rule: a difference between the C and the Python is a bug and is fixed; a limit that both have is written here, as the guest sees it, and not fixed before the first release. The tests in `tests/test_known_limits.py` pin what can be pinned cheaply, so that a limit changes on purpose. **[run]** means a test of the repository runs it; **[read]** means read in the code only; **[not run]** is said where it applies.

* **IPv6 sockets.** The address records of the WIT are whole (family 0 is IPv4, family 1 is IPv6 with eight numbers, flow and scope) and some checks of addresses are tested: a v6 address on a v4 socket, and a multicast address for a bind or a connect, are `invalid-argument` **[run, `tests/test_wasi_p2_sockets.py`]**; the others of the list in the first part of this file (the unspecified address or port 0 for a connect, an IPv4-mapped IPv6 address) are **[read]**. A socket of the family 1 is made by the system: on a machine with no IPv6 the guest gets `not-supported` from `create-tcp-socket` (and, by the same code, `create-udp-socket`) **[run on a machine with none, `test_ipv6_sockets_follow_the_system`, for TCP; with IPv6 the test checks that the family is kept]**. A whole session over IPv6 (bind, listen, connect, accept, datagrams on `::1`) is **not tested** in either language, because the machines that run the tests may have no IPv6; what happens there is what the system does, and the host adds no handling of its own beyond the address checks.
* **The properties of a listener are not copied to the sockets it accepts.** `accept` takes the connection from the system (`accept()`), makes it non-blocking, and gives the guest a socket of the same `address-family` in the state `connected`; it sets nothing else **[read: `wasi_sockets_tcp_tcp_socket_accept`, and the C twin]**. The WIT says `keep-alive-enabled`, `keep-alive-idle-time`, `keep-alive-interval`, `keep-alive-count`, `hop-limit`, `receive-buffer-size` and `send-buffer-size` are inherited. What the guest reads from the accepted socket is therefore what the system gave it: on Linux the accepted socket inherits the options of the listener socket, so the guest usually sees the inherited values; on another system it may see the defaults. No test pins this, because the result is the system's.
* **`https` in C needs `http_send`.** In C an outgoing request with scheme `https` (or an unset scheme, which is `https`) ends with the future of the answer holding `error-code::internal-error(some("https needs a transport of the embedder (s->http_send): this host has no TLS"))` unless the embedder set `s->http_send`; nothing is sent **[run, `test_http_the_c_has_no_tls`]**. In Python the default transport has TLS (`ssl.create_default_context()`; a certificate that does not verify is `TLS-certificate-error`) **[read; not run: it needs a server with a certificate]**. So this is a difference between the two that is deliberate (an optional TLS backend for C was deferred): a program that uses `https` runs in Python and needs the embedder's transport in C.
* **Bodies of http are whole.** The request is sent when the guest first asks for its answer, the answer is read whole into memory, and the guest then reads it as a stream over bytes; the stream ends with `closed` and `http-error-code` is always `none`. The most a body of a request or of an answer can have is 256 MiB (`MAX_BODY`, `1 << 28`); more is `HTTP-response-body-size` for an answer and, for a request, a stream whose `check-write` stops at the limit **[run: the constant, and an answer over a lowered limit is `HTTP-response-body-size`, `test_http_a_body_is_read_whole_and_limited`]**. The head of an answer is at most 64 KiB (`HTTP-response-header-section-size`) **[read]**. A body that breaks halfway (a connection that closes before `Content-Length`, a bad chunk) fails the request; Wasmtime would give the guest the first part and fail the stream **[read in `tools/wasi_p2_conformance/README.md`; not run here]**.
* **No HTTP/2, no redirects, no proxies.** A request is HTTP/1.1 with `Connection: close` and a connection of its own **[run: `test_http_is_http_1_1_with_one_connection_for_each_request`]**. A 3xx answer is the answer: the guest sees the status and `Location`, and no second request is made **[run: `test_http_a_redirect_is_not_followed`]**. The variables `HTTP_PROXY`, `ALL_PROXY` and the like are not read; the request goes to the authority it names **[run: `test_http_proxy_variables_are_not_read`]**. The same is true of the C twin by construction (one function for the transport) **[read; the C side of these three is not run]**.
* **`BCryptGenRandom` on Windows.** The C source of `wasi:random` on Windows is `BCryptGenRandom(NULL, buf, n, BCRYPT_USE_SYSTEM_PREFERRED_RNG)`, in one call for the whole request; a failure (nonzero) is a trap of the guest (`the source of random bytes failed`); a request of more than 64 MiB is a trap too; the Python twin uses `os.urandom`. The scenario `default_source` of `tests/test_wasi_p2_random.py` runs the default source of the C on every system where a C compiler is found, and the Windows runner of `.github/workflows/test.yml` is one of them if it finds `cc`/`gcc`/`clang`; **I could not see a Windows run, so it is not known to be exercised** **[not run]**. On POSIX the source is `getentropy` (256 bytes at a time) or `/dev/urandom` **[run]**.
* **An import with no function.** The library has one function for each import it knows, the same set in C and in Python (201 functions, which `test_the_c_and_the_python_have_a_function_for_the_same_imports` compares), and **no catch-all**: a name it does not have is not answered. What follows is the generator's: the first user refuses to make the glue (`GenError`: "is not a function of WASI 0.2 that fusedwasi has"), so the module is not built; `a Python host` has no such step for 0.2 yet; in C a glue that named such a function would not compile; in Python a lookup of the name raises `AttributeError`. Not done, and not decided: an import that is linked to a function that answers an error code (`unsupported`) or traps with "not implemented: <name>" (the plan in the first part of this file). A guest that imports a function the host lacks therefore does not start, instead of failing at the call. For WASI 0.1 every call of the snapshot has a function (the four sockets answer `NOTSOCK` for a descriptor that exists and `BADF` for one that does not **[run]**), and `proc_raise` ends the program.
